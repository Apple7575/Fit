# 평가와 실험 계획

- 상태: 초안
- 확정 범위: 2. 성공 지표와 목표
- 관련 결정: [[Decisions/ai/rag-evaluation-metrics]], [[Decisions/ai/qwen-company-context-baseline]]

## 1. 원칙

아키텍처를 먼저 확정하지 않는다. 기능 계약과 측정 지표를 정한 뒤 동일한 평가셋에서
단순한 기준선부터 비교하고, 실패 사례와 실험 결과로 RAG 및 에이전트 구조를 선택한다.

- 비교 대상이 아닌 모델, 프롬프트, 평가셋 조건은 가능한 한 고정한다.
- 한 번의 실험에서 핵심 변수 하나만 바꾼다.
- 모든 후보를 실험하지 않고 관찰된 실패를 개선할 후보만 선택한다.
- 품질뿐 아니라 응답시간, 토큰 사용량과 비용도 함께 측정한다.
- 모든 실험은 동일한 자소서 한 개 단위의 평가 사례로 비교한다.
- 최종 결과는 팀이 후보별 차이와 선택 근거를 한눈에 볼 수 있는 표로 남긴다.

## 2. 성공 지표와 목표

### 2.1 평가 단계

| 단계 | 평가 규모 | 적용 기준 | 목적 |
| --- | --- | --- | --- |
| 파일럿 | 대표 사례 10개 이상 | 안전 기준과 출력 형식 | 프롬프트·스키마 오류를 빠르게 발견 |
| 본 평가 | 주요 판정값마다 정답 단위 5개 이상 | 안전 기준과 품질 기준 | 기준선의 최소 통과 여부 결정 |

파일럿의 품질 수치는 기록하되 표본이 작으므로 통과 여부를 결정하는 근거로 사용하지 않는다.
본 평가 전에 특정 판정값의 정답이 부족하면 해당 지표를 산출하지 않고 평가셋을 보강한다.

### 2.2 평가 단위

| 단위 | 정의 |
| --- | --- |
| 기업 주장 | 자소서에서 외부 기업 자료로 확인할 수 있는 독립적인 주장 한 개 |
| 직무 요구사항 | 채용 공고에서 독립적으로 평가할 수 있도록 분리한 요구사항 한 개 |
| 연결 판정 | 기업 주장 또는 직무 요구사항과 자소서 내용 사이의 판정 한 개 |
| 근거 | 하나의 판정에 사용한 DART·뉴스·채용 공고의 원문 구간 한 개 |
| 응답 | 평가 사례 하나에 대해 생성된 전체 구조화 출력 한 개 |

### 2.3 품질 지표

| 기능 | 지표 | 계산 또는 판정 방법 |
| --- | --- | --- |
| 기업 맥락 | 기업 주장 추출 F1 | 정답 주장과 의미가 일치한 추출 결과의 Precision·Recall 조화평균 |
| 기업 맥락 | 사실 판정 Macro F1 | `SUPPORTED`, `PARTIALLY_SUPPORTED`, `CONTRADICTED`, `NOT_VERIFIABLE`별 F1 평균 |
| 기업 맥락 | 기업 연결 판정 Macro F1 | 사실 확인이 가능한 주장에서 `DIRECT`, `INDIRECT`, `DISCONNECTED`, `NOT_APPLICABLE`별 F1 평균 |
| 기업 맥락 | 근거 적합률 | 판정 내용을 직접 뒷받침하거나 반박하는 근거 수 ÷ 제시한 전체 근거 수 |
| 기업 맥락 | 근거 재현율 | 정답 판정에 필요한 근거 중 모델이 제시한 근거 비율 |
| 직무 연결 | 직무 요구사항 추출 F1 | 정답 요구사항과 의미가 일치한 추출 결과의 Precision·Recall 조화평균 |
| 직무 연결 | 요구사항 유형 정확도 | 유형을 맞힌 요구사항 수 ÷ 정답과 매칭된 요구사항 수 |
| 직무 연결 | 직무 연결 판정 Macro F1 | `DIRECT`, `PARTIAL`, `KEYWORD_ONLY`, `NO_EVIDENCE`, `NOT_ASSESSABLE`별 F1 평균 |
| 공통 | 구조화 출력 성공률 | JSON 스키마 검증을 통과한 응답 수 ÷ 전체 응답 수 |

추출 결과는 단어가 일부 겹치는지만 보지 않고 같은 사실이나 요구사항을 가리키는지 사람이
확인해 정답 단위와 연결한다. 정답 라벨은 한 명이 작성하고 다른 한 명이 검토하며,
불일치는 합의한 최종 라벨과 변경 이유를 남긴다.

### 2.4 안전 최소 기준

다음 항목은 파일럿과 본 평가 모두에서 한 건이라도 발생하면 기준선이 실패한 것으로 본다.

| 치명적 오류 | 최소 통과 기준 |
| --- | ---: |
| 자소서에 없는 사용자 경험·행동·성과 생성 | 0건 |
| 제공된 자료에 없는 기업 사실이나 직무 요구사항을 사실로 생성 | 0건 |
| 다른 기업·직무의 자료를 현재 대상의 근거로 사용 | 0건 |
| 원문에 없는 문장을 근거 인용문으로 생성 | 0건 |
| 근거가 없는데 `SUPPORTED` 또는 `DIRECT`로 단정 | 0건 |

구조화 출력 성공률은 `100%`를 최소 기준으로 둔다. 스키마 오류는 재시도로 복구하더라도
최초 응답 실패와 최종 복구 여부를 각각 기록한다.

### 2.5 초기 품질 최소 기준

아래 수치를 첫 본 평가에 적용할 초기 최소 기준으로 사용한다. 기준선 결과에 맞춰 임의로
낮추지 않으며, 정답 분포 부족이나 사람 간 판정 불일치로 지표 자체가 유효하지 않을 때만
재검토하고 변경 이유를 결정 기록에 남긴다.

| 지표 | 초기 최소 기준 |
| --- | ---: |
| 기업 주장 추출 F1 | 0.80 이상 |
| 사실 판정 Macro F1 | 0.75 이상 |
| 기업 연결 판정 Macro F1 | 0.70 이상 |
| 근거 적합률 | 0.90 이상 |
| 직무 요구사항 추출 F1 | 0.80 이상 |
| 요구사항 유형 정확도 | 0.85 이상 |
| 직무 연결 판정 Macro F1 | 0.70 이상 |

기업·직무 연결 판정은 사실 추출보다 해석 차이가 클 수 있어 임시 기준을 낮게 잡았다.
사람 검토자 사이의 판정이 자주 다르면 모델 기준을 낮추기 전에 라벨 정의와 사례를 먼저
보완한다.

### 2.6 운영 지표

- 사례별 입력·출력 토큰 수
- 전체 토큰 수와 추정 비용
- 응답시간의 평균, p50과 p95
- 최초 JSON 스키마 실패율과 재시도 횟수

모델, 실행 환경과 예상 트래픽을 정하지 않았으므로 응답시간·토큰·비용의 최소 통과값은
아직 정하지 않는다. 같은 환경에서 후보 간 상대 차이를 먼저 기록한다.

### 2.7 RAG 추가 후 측정할 검색 지표

최소 기준선은 고정 근거를 입력받으므로 검색 지표를 측정하지 않는다. RAG를 추가한
실험부터 다음 지표를 사용한다.

- Recall@5
- Precision@5
- 다른 기업 문서 포함률
- 기준일이 지난 채용 공고 포함률
- 검색 응답시간

## 3. 데이터 요구사항과 확보 가능성

- 필요한 데이터와 현재 보유 데이터를 비교한다.
- 추가 수집 데이터와 출처 신뢰도를 확인한다.
- 최신성, 이용 조건, 원문 저장 가능 여부를 확인한다.
- 사용자 문서의 저장·삭제·격리 등 개인정보 처리 범위를 정한다.
- 출처가 충돌할 때 적용할 우선순위를 정한다.

| 데이터 또는 판단 | 우선 검토할 처리 방식 |
| --- | --- |
| 재무 수치와 기업 기본 정보 | 구조화 DB 조회 |
| DART 사업보고서 본문과 현재 보유한 뉴스 | 기준선은 고정 입력, 이후 RAG 검색 |
| 채용 공고 | 현재 데이터셋 없음. 기준선은 수동 입력, 이후 확보 가능성 조사 |
| 이력서, 자소서, 프로젝트, 이전 대화 | 사용자별 문서 검색 및 대화 상태 |
| 문항별 평가 기준 | 버전을 관리하는 평가 루브릭 |
| 글자 수와 명시된 제출 조건 | 규칙 기반 검사 |
| 역할별 분석 결과 | 구조화된 에이전트 상태 전달 |

RAG는 근거 검색을 담당한다. 경험과 직무의 연결 판정, 문항 충족도 평가, 수정 우선순위
결정은 검색 결과를 사용하는 별도의 판단 단계다.

직무 연결 분석을 서비스 기능으로 제공하려면 채용 공고의 지속적인 확보, 원문 저장 가능
여부, 기업·직무 식별, 게시일·마감일 관리와 갱신 방식을 확인해야 한다. 이 조건이 충족되지
않으면 MVP에서도 사용자가 공고 원문을 제공하는 방식으로 범위를 제한한다.

## 4. 평가 데이터셋

대표 입력, 정답 근거, 기대 판단과 금지 결과를 묶은 평가 사례를 구현 전에 만든다.

```yaml
입력:
  기업: 삼성전자
  직무: AI 엔지니어
  자소서: 사용자 작성 예시
  채용공고: 평가 대상 공고

정답_근거:
  - 공고의 모델 평가 관련 문장
  - 공고의 Python 개발 관련 문장

기대_판단:
  - 데이터 전처리 경험은 연결 근거 있음
  - 모델 배포 경험은 확인할 수 없음

금지_결과:
  - 공고에 없는 역량을 필수라고 판단
  - 사용자에게 없는 성과 수치 생성
```

검색 평가지표를 사용하려면 질의마다 관련 문서를 표시한 검색 정답지도 함께 만든다.

## 5. 최소 기준선

```yaml
입력:
  - 대상 기업 한 개
  - 대상 직무 한 개
  - 자소서 문항 한 개
  - 자소서 초안 한 개
  - 평가용으로 고정한 기업·직무 근거
처리:
  - 단일 에이전트와 단일 프롬프트 사용
  - 기업 맥락 연결과 직무 연결 분석을 한 번에 수행
  - 벡터 DB, 리랭커, 질문 재작성과 다중 에이전트는 사용하지 않음
출력:
  - 자소서 주장
  - 관련 기업·직무 근거
  - 연결 판정
  - 판정 이유
  - 근거가 없어 확인할 수 없는 내용
```

이 기준선은 검색 기술의 성능보다 기능 계약과 평가 방법을 빠르게 검증하기 위한 것이다.
이후 기본 검색을 붙인 후보와 비교해 검색이 실제 품질을 높이는지 확인한다.

## 6. 실패 분석과 개선 가설

기준선의 실패를 유형화하고 관찰한 실패에 대응하는 가설을 세운다.

- 다른 기업의 문서가 검색됨
- 오래된 채용 공고가 검색됨
- 문항과 무관한 긴 문서가 검색됨
- 정확한 기술명이 의미 검색에서 누락됨
- 사용자 경험의 행동보다 기술 키워드만 매칭됨
- 검색 근거에 없는 역량을 LLM이 추가함

```yaml
문제: 다른 기업의 유사 직무 공고가 검색됨
가설: 기업과 공고 유효기간 필터가 목표 기업의 최신 공고 검색률을 높일 것이다
독립변수: 메타데이터 필터 적용 여부
측정지표:
  - Recall@5
  - 잘못된 기업 문서 포함률
  - 검색 응답시간
```

## 7. RAG 개선 실험 후보

- 임베딩 모델
- 문서 분할 크기와 중첩
- 문서 유형별 분할 전략
- 벡터·키워드·하이브리드 검색
- 메타데이터 필터
- 리랭커
- 질문 재작성
- 검색 문서 수
- 기업·직무·기간별 인덱스
- 사용자 문서와 기업 문서의 검색 공간 분리

## 8. 에이전트 구조 실험

안정된 검색 기준선에서 다음 구조를 동일한 평가셋으로 비교한다.

```yaml
구조_A: 단일 에이전트가 검색·평가·첨삭 수행
구조_B: 검색 분석과 첨삭을 분리
구조_C: 기업·직무·경험 분석 후 총괄 에이전트가 종합
```

근거 충실도, 피드백 중복률, 역할 간 판단 충돌률, 행동 가능한 피드백 비율, 응답시간,
토큰 사용량과 비용을 비교한다. 다중 에이전트가 품질이나 오류 추적 가능성을 개선하지
못하면 역할은 논리적으로만 분리하고 실행 에이전트는 합친다.

## 9. 아키텍처 확정과 운영 검증

선택한 검색, 저장, 평가, 오케스트레이션 구조마다 실험 근거를 기록한다. 확정 후에는
다음 항목을 검증한다.

- 백엔드 API 연결
- 사용자별 문서 격리
- 개인정보 저장과 삭제
- 응답시간과 비용
- 데이터 갱신과 재색인
- 실패 모니터링
- 사용자 테스트
- 평가셋 회귀 테스트

## 10. 실험 결과 산출물

실험 결과는 원시 로그만 남기지 않고 Markdown 요약표와 재계산 가능한 CSV로 함께
관리한다. 각 수치는 사용한 평가셋 버전과 실행 조건을 추적할 수 있어야 한다.

### 10.1 후보별 종합 비교표

#### 기업 맥락 품질

두 실행의 연결 지표는 수정된 v2 정답 기준으로 다시 계산했다. `NOT_VERIFIABLE` 주장은
