# JD 연결 분석 기준선 평가 결과

## 평가 방식

각 JD 역할과 사용자 경험 연결을 한 건씩 Qwen에 전달했다. JD 전체 대신 해당 역할이 참조하는 원문 섹션을 유지했고, Qwen은 필요한 근거별 `PRESENT` 또는 `ABSENT`와 사용자 원문 인용을 반환했다. Python이 근거 충족 상태로 최종 라벨을 산출했다.

Qwen이 반환한 `PRESENT` 인용문이 사용자 원문에 없으면 해당 연결을 계약 실패로 처리했다. 계약 실패는 평가에서 제외하지 않고 오답으로 계산했다.

## 전체 회귀 평가

| 지표 | 결과 |
|---|---:|
| 사례 | 5 |
| 연결 | 55 |
| Prediction coverage | 0.9818 |
| Label Accuracy | 0.9091 |
| Label Macro F1 | 0.9079 |
| 필요 근거 Precision | 0.9231 |
| 필요 근거 Recall | 0.9600 |
| 존재하지 않는 인용문 비율 | 0.0000 |
| 계약 실패 | 1건 |
| 총 토큰 | 71,730 |
| 연결당 평균 토큰 | 1,304.18 |

`hallucinated_quote_rate=0`은 계약 검증을 통과한 인용문에 존재하지 않는 문장이 없었다는 의미다. Qwen이 잘못된 인용문을 생성한 1건은 검증기가 차단해 prediction coverage가 `0.9818`로 내려갔다.

## 실패 유형

### 조건 없는 일반 경험을 조건부 경험으로 인정

토스뱅크의 대규모 트래픽·높은 SLA 요구에서 일반적인 API 운영과 모니터링을 `해당 조건의 프로덕션 운영`으로 인정했다. 규모나 SLA 조건이 없으므로 `NOT_SUPPORTED`여야 하지만 `PARTIALLY_SUPPORTED`로 판정했다.

### 관련 활동을 명시적 수행으로 확대 해석

카카오모빌리티 사례에서는 주행 로그 분석과 재현 시나리오 작성을 자율주행 시스템 테스트 수행으로 확대 해석했다. 폐쇄장·실도로 환경뿐 아니라 실제 테스트 수행도 명시되지 않았다.

삼성전자 SW 사례에서도 전처리 파이프라인과 추론 API 구현을 테스트 스크립트 구현 및 품질관리 방법으로 각각 확대 해석했다.

### 잘못된 인용문 생성

삼성전자 `직무 연관 경험` 한 건에서 Qwen이 사용자 원문에 그대로 존재하지 않는 인용문을 두 번 반환했다. 실행기는 이를 결과로 채택하지 않고 계약 실패로 기록했다.

## 판단

현재 기준선은 인용문 존재 검증과 명확한 `SUPPORTED` 탐지에는 사용할 수 있다. 다기업 신규 사례의 Macro F1 `0.7222`와 반복된 과대 판정 때문에 서비스가 단정적인 적합성 판정을 제공하기에는 아직 부족하다.

다음 개선은 같은 9건의 점수를 올리는 프롬프트 튜닝보다 조건부 근거 관계와 명시적 행동 판단을 데이터 계약에 표현하는 방향으로 진행한다. 개선 방식은 새로운 미사용 JD·경험 평가셋에서 다시 검증한다.

## 산출 방법

개별 실행은 `run_jd_pairwise_evidence_judge.py`, 통합 지표는 `aggregate_jd_pairwise_runs.py`로 계산했다. 실행 결과 JSON은 Git에 포함하지 않는 `outputs/jd-coaching`에 저장했다.
