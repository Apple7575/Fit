- 상태: 설계 중
- 현재 단계: 데이터 요구사항과 확보 가능성 조사
- 최종 갱신일: 2026-09-08

## 1. 문서 목적

이 문서는 자소서 피드백 서비스가 해결할 사용자 문제와 제공할 가치를 정의한다. 각
가치를 실제 기능으로 검증할 수 있도록 입력, 판단, 결과와 실패 조건을 기능 계약으로
구체화한다.

기술, RAG 구성과 에이전트 수는 이 문서의 결정을 바탕으로 이후 실험에서 정한다.

관련 결정: [[Decisions/ai/rag-mvp-feature-contracts]]

## 문서 읽는 순서

1. `결정 요약`에서 현재 확정된 범위를 확인한다.
2. `MVP 사용자 문제`와 `MVP 이용 범위`에서 해결할 문제와 경계를 확인한다.
3. `가치 구조`에서 문제별 책임과 사용자 결과를 확인한다.
4. `기능 계약`에서 각 가치를 검증 가능한 기능으로 구체화한다.
5. `남은 작업`에서 다음 검토 대상을 확인한다.

## 3. MVP 사용자 문제

### 3.1 문제 가설

아래 네 상황은 사용자 조사로 검증된 사실이 아니라 현재 서비스 아이디어에서 도출한
가설이다. 이후 사용자 테스트에서 발생 빈도와 중요도를 검증한다.

| 사용자 문제 | 사용자가 겪는 어려움 | 연결되는 가치 |
| --- | --- | --- |
| 경험과 기여가 구체적이지 않음 | 팀 성과는 설명하지만 자신의 행동과 판단을 설명하지 못함 | 대화를 통한 경험 발굴 |
| 기업과 지원 이유가 연결되지 않음 | 기업 정보를 나열하지만 자신의 경험과 연결하지 못함 | 기업 맥락 연결 |
| 경험과 직무의 연결을 판단하기 어려움 | 공고의 요구사항을 어떤 경험이 증명하는지 찾지 못함 | 직무 연결 분석 |
| 문제를 실제 수정으로 옮기기 어려움 | 피드백을 받아도 무엇부터 어떻게 고칠지 모름 | 진단에서 수정까지 연결 |

네 문제 가설은 유지하지만 같은 시점에 모두 구현하지 않는다. 1차 MVP에서는 외부 근거가
필요하고 일반적인 LLM 첨삭과 차별성이 큰 `기업 맥락 연결`과 `직무 연결 분석`을 먼저
검증한다. `대화를 통한 경험 발굴`과 `진단에서 수정까지 연결`은 이 분석 결과를 바탕으로
사용자와 상호작용하는 후속 단계로 둔다.

### 3.2 대표 사용자 상황

> 지원 기업과 직무를 정한 취업준비생이 작성한 자소서 한 개를 제출하고, 자소서에 사용한
> 기업 정보와 자신의 경험이 기업·직무 근거에 적절히 연결됐는지 확인한다.

## 4. MVP 이용 범위

### 4.1 지원 세션

하나의 지원 세션은 특정 기업·직무에 제출할 자소서 한 개를 분석하는 전체 대화 맥락이다.
여기서 세션은 모델의 컨텍스트 길이가 아니라 서비스가 같은 분석 대상으로 묶어 관리하는
논리적 작업 단위다.

```yaml
지원_세션:
  대상_기업: 한 개
  대상_직무: 한 개
  대상_자소서: 한 개
  필수_자료:
    - 자소서 문항
    - 자소서 초안
  근거_자료:
    - 서비스가 보유한 DART·뉴스 기업 자료
    - 사용자 또는 평가자가 제공한 실제 채용 공고 원문
  선택_자료:
    - 이력서
    - 프로젝트 경험 설명
```

- 같은 자소서에 대한 기업·직무 분석 질문은 같은 세션에서 다룬다.
- 기업, 직무 또는 대상 자소서가 바뀌면 새 지원 세션을 시작한다.
- 여러 문항과 자소서 전체의 일관성 분석은 후속 범위다.

### 4.2 사용자 대화 방식

사용자는 기본적으로 총괄 코치와 대화한다. 1차 기준선에서는 단일 에이전트가 총괄 코치와
기업·직무 분석 역할을 함께 수행한다. 사용자는 기업 맥락 또는 직무 연결 관점을 선택할
수 있지만, 내부 실행 에이전트는 분리하지 않는다.

사용자에게 보이는 역할과 실제 실행 에이전트 수는 별개의 결정이다.

### 4.3 요청별 입력

| 사용자 요청 | 필요한 정보 |
| --- | --- |
| 기업 맥락 연결 | 대상 기업, 자소서 문항·초안, 기업 근거 자료 |
| 직무 연결 분석 | 대상 직무, 자소서 문항·초안, 실제 채용 공고 원문 |
| 경험 구체화 | 후속 단계. 대화, 이력서, 프로젝트 설명 또는 자소서의 경험 정보 |
| 자소서 진단·첨삭 | 후속 단계. 앞 단계의 분석 결과와 자소서 문항·초안 |

1차 MVP의 모든 지원 세션에는 대상 기업, 대상 직무, 자소서 문항과 초안이 필요하다.
기업 근거는 서비스가 보유한 DART·뉴스에서 제공한다. 현재 채용 공고 데이터셋과 자동
수집 경로가 없으므로 직무 연결 분석의 기준선에서는 사용자 또는 평가자가 실제 공고
원문을 직접 제공한다.

### 4.4 포함 범위와 후속 범위

| 구분 | 기능 |
| --- | --- |
| 1차 MVP | 기업 맥락 연결 |
| 1차 MVP | 직무 연결 분석 |
| 후속 | 대화를 통한 경험 발굴 |
| 후속 | 진단에서 수정까지 연결 |
| 후속 | 기존 초안 안에서 소재 순서와 구조 개선 |
| 후속 보조 기능 | 명시된 글자 수와 제출 조건 검사 |
| 후속 | 초안 없이 완성된 자소서를 처음부터 대신 작성 |
| 후속 | 이력서와 여러 자소서 문항 전체의 일관성 검증 |
| 후속 | 여러 기업에 맞춘 자소서 일괄 변환 |

## 5. 가치 구조

### 5.1 평가 기준

| 기준 | 확인할 질문 |
| --- | --- |
| 사용자 문제의 명확성 | 취업준비생의 어떤 문제를 해결하는가? |
| 결과의 행동 가능성 | 사용자가 결과를 받고 실제로 무엇을 고칠 수 있는가? |
| 다른 가치와의 독립성 | 다른 역할과 구분되는 결과가 있는가? |
| 근거 가능성 | 확보 가능한 데이터와 사용자 답변으로 판단할 수 있는가? |
| 서비스 차별성 | 일반적인 문장 첨삭보다 기업 데이터와 대화 구조가 의미 있는가? |
| 판단 한계의 통제 | 알 수 없는 내용을 내부 기준이나 합격 가능성처럼 말하지 않는가? |

### 5.2 전체 보기

| 가치 | 범위 | 책임 역할 후보 | 사용자에게 주는 결과 |
| --- | --- | --- | --- |
| 소재와 구조 설계 | 후속 | 소재·구조 설계 코치 | 추천 경험, 핵심 주장과 문단 개요 |
| 기업 맥락 연결 | 1차 MVP | 기업 맥락 분석 역할 | 기업 관련 주장의 근거와 지원 이유의 연결 |
| 직무 연결 분석 | 1차 MVP | 직무 연결 분석 역할 | 요구사항과 연결되는 경험 및 부족한 설명 |
| 대화를 통한 경험 발굴 | 후속 | 경험 발굴 코치 | 누락 정보에 대한 질문과 구조화된 경험 |
| 진단에서 수정까지 연결 | 후속 | 문항 평가자·첨삭가 | 문제 우선순위, 수정안과 수정 이유 |
| 지원서 전체 일관성 | 후속 | 지원서 일관성 검증가 | 문서 간 충돌, 반복과 빠진 역량 |

### 5.3 소재와 구조 설계

사용자가 가진 경험 중 기업·직무·문항에 적합한 소재를 찾고 핵심 주장과 구조를 설계한다.
후속 단계에서는 기존 초안의 소재 순서와 구조 개선까지만 포함한다. 초안 없이 완성문을 대신
작성하는 기능은 후속 범위다.

### 5.4 기업 맥락 연결

공개된 기업 자료로 자소서의 기업 관련 주장이 맞는지 확인하고, 해당 정보가 사용자의
지원 이유를 실제로 뒷받침하는지 분석한다.

- 1차 MVP 근거: DART 공시·사업보고서, 현재 보유한 뉴스 데이터
- 결과: 주장의 근거 여부, 지원동기와의 관련성, 출처와 수정 제안

재무 수치만으로는 지원동기를 충분히 설명하기 어렵다. 사업 내용, 제품과 기술,
연구개발 방향과 사업부 정보를 DART 본문과 뉴스에서 어느 정도 확보할 수 있는지 먼저
검증한다. 기업 공식 자료와 다른 공공기관 자료는 1차 MVP 데이터 범위에서 제외한다.

### 5.5 직무 연결 분석

실제 채용 자료에서 요구사항을 찾고 사용자 경험이 이를 보여주는지 분석한다.

- 1차 MVP 근거: 대상 기업·직무의 실제 채용 공고 한 개
- 결과: 연결 근거가 있는 경험, 부분 근거, 확인되지 않는 요구사항과 보완 질문

현재 프로젝트에는 채용 공고 데이터가 없으므로 기준선 구현 전에 대표 공고를 수동으로
확보해야 한다. DART와 뉴스, 다른 기업의 유사 공고 또는 일반적인 직무 지식으로 요구
역량을 만들지 않으며 합격 적합성을 판정하지 않는다.

### 5.6 대화를 통한 경험 발굴

경험에서 빠진 상황, 행동, 판단 이유, 본인의 기여와 결과를 질문으로 이끌어낸다. 이미
제공된 내용을 반복해서 묻지 않고 가장 중요한 누락 정보부터 확인한다.

### 5.7 진단에서 수정까지 연결

문항 충족도, 경험의 구체성, 기업·직무 연결성을 진단하고 사용자에게 확인된 사실만으로
수정 우선순위와 개선안을 만든다.

수정 우선순위는 사실 보존, 문항 충족, 본인 기여, 근거 구체성, 직무 연결, 기업 연결,
논리 구조, 제출 조건, 문장 표현 순이다.

### 5.8 지원서 전체 일관성

이력서와 여러 자소서 문항의 기간, 수치, 역할, 경험 배치를 비교한다. 여러 문서의 저장과
교차 분석이 필요하므로 후속 범위로 둔다.

## 6. 보조 기능과 시스템 책임

### 6.1 제출 조건 검사

글자 수, 필수 항목, 기업명, 직무명과 공고에 명시된 작성 조건을 확인한다. 명시된 조건은
규칙 기반으로 검사하고 애매한 경우에만 LLM이 설명한다.

### 6.2 피드백 조정

총괄 코치는 다음 책임을 가진다.

- 중복된 피드백을 병합한다.
- 충돌하는 피드백을 표시하거나 해소한다.
- 사실 오류와 문항 미충족을 표현 문제보다 우선한다.
- 다음에 물어볼 질문과 호출할 전문 역할을 선택한다.
- 최종 수정 순서를 제시한다.

## 7. 공통 판단 범위

### 7.1 서비스가 판단하지 않는 것

- 실제 합격 가능성
- 기업 내부의 서류 평가 점수와 배점
- 공개되지 않은 조직 문화와 채용담당자의 선호
- 사용자에게 확인되지 않은 경험과 성과
- 다른 지원자 대비 경쟁력

### 7.2 근거 처리 원칙

- 기업 관련 사실은 출처와 기준일을 보존한다.
- 사용자 경험은 사용자 발화와 제출 문서만 사실 근거로 사용한다.
- 모델의 해석은 사용자 사실과 구분한다.
- 근거가 부족하면 추정하지 않고 미확인 상태로 표시한다.

근거, 결과, 상호작용, 성공·실패 조건과 판단 범위를 포함한다.
