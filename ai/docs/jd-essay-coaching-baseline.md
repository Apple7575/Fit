## 목표

채용 자료에서 확인되는 역할과 역량을 근거로 추출하고, 사용자의 경험이 해당 근거와 연결되는지 판정한다. 직무명에 대한 일반적인 LLM 지식을 정답으로 사용하지 않는다.

## 이번 범위

- JD 자료 계약과 출처 메타데이터
- JD 역할 요소 추출
- 사용자 경험과 역할 요소 연결
- 연결 판정 루브릭과 평가 사례

문항 첨삭, 기업 뉴스, 재무 정보, 기업 사실 검증, 멀티에이전트 분리는 이번 기준선에 포함하지 않는다.

## 확보한 공식 자료

| 자료 | 확인 내용 | 사용 범위 |
|---|---|---|
| 삼성전자 DS부문 관계사 페이지 | `S/W 개발` 직무 설명, 수행 업무, 필요 역량 | `OFFICIAL_JOB_DESCRIPTION` |
| 삼성전자 DS부문 관계사 페이지 | 열정, 창의혁신, 인간미·도덕성 | `TALENT_PROFILE` |
| 삼성전자 DS부문 2026년 대학생 인턴 직무기술서 | Global Manufacturing & Infra총괄의 직무, 수행 업무, 지원 자격, 우대 사항 | `JOB_POSTING` |

## 데이터 계약

자료 유형은 다음 세 가지를 분리한다.

```text
JOB_POSTING              실제 채용 공고와 공고별 직무기술서
OFFICIAL_JOB_DESCRIPTION 회사가 제공하는 상시 직무 소개
TALENT_PROFILE           회사 공통 인재상
```

각 문서는 기업, 조직, 직무, 출처 URL, 확인일, 게시일, 마감일과 원문 섹션을 보존한다. 게시일이나 마감일을 확인하지 못했으면 추정하지 않고 `null`로 기록한다.

원문 섹션 유형:

```text
JOB_SUMMARY
RESPONSIBILITY
REQUIRED_QUALIFICATION
PREFERRED_QUALIFICATION
TALENT_VALUE
OTHER
```

## 평가 단위

기준선은 두 단계를 따로 평가한다.

1. 원문에서 역할 요소를 근거와 함께 추출했는가
2. JD 근거와 사용자 경험 근거를 모두 사용해 연결했는가

JD 원문 한 문장에 요구사항이 여러 개 있으면 각각 독립적으로 확인할 수 있는 원자적 역할 요소로 분리한다. 연결 판정 단위는 `역할 요소 1개 × 사용자 경험 1개`다.

각 역할 요소에는 연결을 입증하는 증거 요구사항을 둔다. 사용자 경험에 모든 요구사항이 명시되면 `SUPPORTED`, 일부만 명시되면 `PARTIALLY_SUPPORTED`, 하나도 명시되지 않으면 `NOT_SUPPORTED`다. 주제나 키워드가 유사하다는 이유만으로 연결하지 않는다.

모든 판정은 다음 내용을 함께 반환해야 한다.

- JD의 `section_id`
- 사용자의 `experience_id`
- 충족된 증거 요구사항과 사용자 원문 인용
- 확인되지 않은 증거 요구사항
- 연결 라벨과 판정 이유

## 판정 정책과 평가 루브릭

서비스 판정 규칙과 시스템 평가 기준은 별도 파일로 관리한다.

| 파일 | 책임 |
|---|---|
| `connection-policy-v1.json` | 서비스가 세 연결 라벨을 선택하는 규칙 |
| `evaluation-rubric-v1.json` | LLM Judge가 설명 품질을 평가하는 기준 |

연결 라벨의 정확성은 LLM Judge에게 맡기지 않는다. 사람이 확정한 정답 라벨과 서비스 라벨을 코드로 비교해 Accuracy와 Macro F1을 계산한다.

LLM을 사용하는 평가는 두 용도로 구분한다.

| 평가기 | 입력과 출력 | 용도 |
|---|---|---|
| 필요 근거 Judge | 각 증거 요구사항에 대해 `PRESENT` 또는 `ABSENT`, 사용자 원문 인용 | 초안 라벨의 사전 검토 |
| 설명 품질 Judge | `evaluation-rubric-v1.json`에 따라 항목별 0~2점 | 서비스가 생성한 설명의 품질 평가 |

필요 근거 Judge는 최종 연결 라벨을 반환하지 않는다. Python이 모든 근거가 있으면 `SUPPORTED`, 일부만 있으면 `PARTIALLY_SUPPORTED`, 하나도 없으면 `NOT_SUPPORTED`로 계산한다. 초안과 Judge 계산 결과가 다른 항목만 사람이 검토한다. 사람 검토 전 결과는 정답 라벨이나 성능 측정값으로 사용하지 않는다.

설명 품질 Judge는 JD 근거 충실성, 사용자 경험 근거 충실성, 라벨과 설명의 일관성, 누락 정보의 명확성만 평가한다. 두 Judge 모두 새로운 직무 요구사항이나 사용자 경험을 보충해서는 안 된다.

초기 평가 사례는 데이터 흐름을 검증하기 위한 합성 사례다. 역할 요소, 증거 요구사항과 연결 라벨을 사람이 검토한 뒤 `label_status=HUMAN_APPROVED`로 확정했으므로 기준선 점수 계산에 사용할 수 있다. 사례가 한 건뿐이므로 이 결과를 일반적인 성능으로 해석하지 않는다.

## 전체 문서 연결 기준선

첫 기준선은 역할 요소 추출과 경험 연결을 한 번에 평가하지 않는다. 사람이 확정한 역할 요소와 평가 대상 조합을 모델에 제공하고, 전체 JD 원문을 읽은 모델이 경험 연결 라벨과 근거를 판정하게 한다. 정답 라벨과 정답 근거는 모델 입력에서 제외한다.

이 방식은 경험 연결 판정의 실패를 역할 요소 추출 실패와 분리하기 위한 통제 실험이다. 역할 요소 추출은 별도의 평가 사례가 확보된 뒤 측정한다.

실행 예:

```powershell
python -m ai.scripts.run_jd_connection_baseline `
  --env-file ai/.env `
  --output outputs/jd-coaching/full-document-fixed-role-baseline.json
```

결과에는 Accuracy, Macro F1, 라벨별 Precision·Recall·F1과 오답 조합이 기록된다.

## 필요 근거 분해 Judge

실제 JD 평가 사례에서는 초안 연결 라벨과 이유를 모델 입력에서 제거한다. 모델에는 역할 요소, 역할 요소별 증거 요구사항, 사용자 경험, 평가 대상 조합만 제공한다. 모델은 세부 근거의 존재 여부와 정확한 사용자 원문 인용만 반환하고, 코드는 응답 구조와 인용문을 검증한 뒤 연결 라벨을 산출한다.

실행 예:

```powershell
python -m ai.scripts.run_jd_evidence_judge `
  --env-file ai/.env `
  --output outputs/jd-coaching/actual-jd-evidence-judge.json
```

2026-09-12 최초 실행에서는 20개 연결 조합 중 초안과 18개가 일치하고 2개가 불일치했다. `데이터 마이닝`은 예측 모델의 정량적 개선 결과를 인정해 `SUPPORTED`, `SW·HW 플랫폼 활용 프로젝트`는 FastAPI를 플랫폼으로 단정하지 않아 `NOT_SUPPORTED`로 사람이 확정했다.

이 사례는 충돌을 해결할 때 동일한 Judge 결과를 참고했으므로 `ADJUDICATION_SET`으로 취급한다. 확정 라벨과의 점수를 계산할 수는 있지만 독립적인 모델 성능으로 보고하지 않는다. 실제 성능은 이 과정에서 사용하지 않은 별도 평가 사례로 측정한다.

첫 독립 평가셋은 같은 실제 JD에 새 합성 경험 6개와 연결 조합 18개를 추가한 `HOLDOUT_EVALUATION`이다. `SUPPORTED`, `PARTIALLY_SUPPORTED`, `NOT_SUPPORTED`를 각각 6개씩 구성했고, Qwen 실행 전에 사람이 18개 초안 라벨을 모두 동일하게 검토해 `HUMAN_APPROVED`로 확정했다.

이 후보는 동일 JD에서 새로운 사용자 경험을 판정하는 능력만 측정한다. 다른 회사나 직무의 JD에도 일반화되는지는 이후 별도 JD 평가셋으로 측정한다.

2026-09-13 최초 Qwen 실행 결과는 18개 중 14개 정답, Accuracy `0.7778`, Macro F1 `0.75`다. `SUPPORTED`와 `NOT_SUPPORTED`는 각각 6개를 모두 맞혔지만 `PARTIALLY_SUPPORTED`는 6개 중 2개만 맞혔다. 나머지 4개는 모두 `NOT_SUPPORTED`로 과소 판정했다.

오답에서는 경험에 데이터 유형이나 분석 대상이 명시돼 있어도 핵심 직무 개념이 부족하면 관련 세부 근거를 전부 `ABSENT`로 처리하는 경향이 나타났다. 다음 비교에서는 동일 평가셋으로 직접 라벨 기준선도 실행해 이 문제가 근거 분해 방식의 지시 문제인지 모델 자체의 의미 판정 문제인지 구분한다.

같은 평가셋의 직접 라벨 기준선도 18개 중 14개를 맞혀 Accuracy `0.7778`, Macro F1 `0.7381`을 기록했다. 두 방식 모두 `PARTIALLY_SUPPORTED` 6개 중 2개만 맞혔지만 오답 유형은 달랐다.

| 방식 | Accuracy | Macro F1 | `PARTIALLY_SUPPORTED` Recall | 정확한 근거 인용 | 총 토큰 |
|---|---:|---:|---:|---:|---:|
| 필요 근거 분해 | 0.7778 | 0.7500 | 0.3333 | 18/18, 100% | 7,574 |
| 직접 라벨 | 0.7778 | 0.7381 | 0.3333 | 22/24, 91.67% | 6,693 |

필요 근거 분해는 라벨 정확도를 높이지 못했지만 모든 인용문이 실제 사용자 경험에 존재해 추적 가능성이 높았다. 직접 라벨은 토큰을 881개 적게 사용했지만 원문 두 곳의 종결어미를 바꿔 인용해 출력 계약 검증에 실패했다. 직접 라벨 방식은 부분 연결을 `SUPPORTED`와 `NOT_SUPPORTED` 양쪽으로 잘못 보냈고, 필요 근거 분해 방식은 네 건을 모두 `NOT_SUPPORTED`로 과소 판정했다.

`PARTIALLY_SUPPORTED` 6개만 대상으로 전체 JD는 유지하고 연결 조합을 한 건씩 나눠 호출한 결과 5개를 맞혀 Recall `0.8333`을 기록했다. 일괄 입력의 Recall `0.3333`보다 높아 여러 조합을 한 번에 판정할 때 세부 근거가 서로 영향을 준다는 가설을 지지한다.

| 부분 연결 판정 방식 | 정답 | Recall | 총 토큰 | 연결당 평균 토큰 |
|---|---:|---:|---:|---:|
| 일괄 입력 | 2/6 | 0.3333 | 7,574* | 420.78* |
| 조합별 입력, 전체 JD 반복 | 5/6 | 0.8333 | 11,998 | 1,999.67 |
| 조합별 입력, 관련 JD 섹션 | 6/6 | 1.0000 | 7,423 | 1,237.17 |

`*` 일괄 입력의 토큰은 부분 연결뿐 아니라 전체 18개 판정을 포함한다. 관련 섹션 방식은 전체 JD 반복 방식보다 토큰을 4,575개, 약 38% 줄이면서 Recall을 높였다. 그러나 6개 판정에 전체 18개 일괄 입력과 비슷한 토큰을 사용하므로 그대로 전체 역할 요소에 확장하면 비용이 커진다.

관련 섹션 방식에서는 이전에 놓쳤던 `Raspberry Pi 4`도 임베디드 대상으로 인정했다. 관련 JD 문맥만 남겨 의미 판정의 잡음을 줄인 효과로 볼 수 있지만 한 번의 6건 실행만으로 안정성을 확정할 수는 없다. 같은 설정의 반복 재현성과 전체 라벨에서의 정확도를 확인해야 한다.

같은 부분 연결 6건을 반복 실행해 다시 6/6을 기록했다. 이어 전체 18건을 관련 섹션·단일 조합 방식으로 실행한 결과 모든 라벨을 맞혀 Accuracy와 Macro F1이 `1.0`이었다.

| 전체 18개 방식 | Accuracy | Macro F1 | 정확한 근거 인용 | 총 토큰 |
|---|---:|---:|---:|---:|
| 필요 근거 일괄 입력 | 0.7778 | 0.7500 | 100% | 7,574 |
| 직접 라벨 일괄 입력 | 0.7778 | 0.7381 | 91.67% | 6,693 |
| 관련 섹션·단일 조합 | 1.0000 | 1.0000 | 100% | 22,148 |

관련 섹션·단일 조합 방식은 일괄 근거 분해보다 토큰을 약 2.92배 사용했다. 정확도는 높지만 현재 형태를 서비스에 그대로 적용하면 비용과 호출 횟수가 크다.

또한 `1.0`은 독립 성능이 아니다. 최초 오답을 분석해 관련 섹션·단일 조합 방식을 선택하고 같은 평가셋에서 다시 측정했으므로 이 평가셋은 이제 `VALIDATION_SET`이다. 최초 일괄 실행의 `0.7778`만 처음 보는 데이터에 대한 결과이고, 최종 방식의 일반화 성능은 새로운 미사용 평가셋에서 다시 측정해야 한다.

## 임의 기업 JD 서비스 API

서비스 MVP는 저장된 삼성전자 JD만 선택하는 방식에서 사용자 제공 JD를 받는 방식으로 확장한다. 기업별 크롤러가 없어도 사용자가 기업명, 직무명과 JD 원문을 지원 컨텍스트로 등록하고, 이력서·자소서·경험·포트폴리오를 연결해 동일한 분석 계약을 사용할 수 있다.

처리 흐름은 다음과 같다.

1. `POST /internal/job-contexts`에서 Qwen이 JD 원문을 최대 8개의 원자적 요구사항으로 구조화한다.
2. 각 요구사항의 `source_quote`가 JD 원문에 실제로 존재하는지 코드가 검증한다.
3. 각 요구사항을 별도 Qwen 호출로 보내 사용자 글에서 확인할 최소 근거를 1~3개 정의한다.
4. 역할명이 JD 원문에 그대로 있으면 더 긴 문장 대신 역할명 자체를 최소 인용으로 사용해 다른 조건의 혼입을 막는다.
5. 구조화 결과와 공고 ID·URL·게시일·마감일·수집일을 PostgreSQL에 저장한다. 같은 공고 ID의 본문이 바뀌면 버전을 올리고 동일한 본문은 재사용한다.
6. `POST /internal/job-contexts/{context_id}/analyses`에서 요구사항 한 건과 사용자 자료를 Qwen에 전달해 근거별 `PRESENT` 또는 `ABSENT`를 판정한다.
7. 요구사항 판정은 기본 최대 4개까지 동시에 실행하고 한 건 실패 시 나머지 성공 결과를 유지한다.
8. 여러 사용자 자료에 분산된 근거를 합치고 각 인용에 `document_id`, 자료 유형과 원문의 `start_offset`·`end_offset`을 남긴다.
9. Python이 근거 충족 상태로 최종 라벨, 보완 행동과 후속 질문을 만든다.
10. 서비스 화면은 비동기 분석 작업을 생성하고 상태 조회 API에서 저장된 완료 결과를 가져온다.

JD에 없는 배포, 운영, 최적화, 오류 처리, 협업, 정량 성과를 필수 근거로 추가하지 않는다. 첫 통합 테스트에서 이 항목들이 과도하게 추가되는 문제가 확인돼 최소 근거 규칙과 3개 상한을 적용했다.

서버 실행:

```powershell
python -m uvicorn ai.jd_coaching.api:app --host 0.0.0.0 --port 8000
```

환경변수 `QWEN_BASE_URL`, `QWEN_MODEL`, `QWEN_API_KEY`를 사용한다. 별도 파일을 사용할 경우 `JD_QWEN_ENV_FILE`에 경로를 지정한다.

요청 예시:

```json
{
  "company_name": "지원 기업",
  "position_name": "백엔드 개발자",
  "jd_text": "Python과 FastAPI를 활용한 REST API 개발 경험이 필요합니다.",
  "applicant_text": "Python과 FastAPI로 REST API를 구현했습니다."
}
```

API 계약은 다음과 같다.

| API | 책임 |
|---|---|
| `POST /internal/job-contexts` | JD 구조화 및 저장, `context_id` 반환 |
| `GET /internal/job-contexts/{context_id}` | 저장한 JD와 요구사항 조회 |
| `POST /internal/job-contexts/{context_id}/analyses` | 구조화 사용자 자료와 요구사항 연결 분석 |
| `POST /internal/job-contexts/{context_id}/analysis-jobs` | 저장되는 비동기 분석 작업 생성, `202 Accepted` 반환 |
| `GET /internal/analysis-jobs/{analysis_id}` | `QUEUED`, `RUNNING`, `COMPLETED`, `FAILED` 상태와 완료 결과 조회 |
| `POST /internal/conversations` | 완료된 분석 결과를 기준으로 지속 대화 생성 |
| `POST /internal/conversations/{conversation_id}/messages` | 이전 맥락을 포함해 코칭 답변 생성, 중복 요청 방지 |
| `GET /internal/conversations/{conversation_id}` | 대화 기준 분석과 메시지 조회 |
| `DELETE /internal/conversations/{conversation_id}` | 지원 세션 삭제 시 AI 대화와 메시지 삭제 |
| `POST /internal/analyses` | 단일 JD·사용자 글을 한 번에 처리하는 동기 분석 API |
| `GET /health` | 서버 프로세스 상태 확인 |

2026-09-13 삼성전자 이름이 없는 합성 JD로 Qwen 통합 테스트를 수행했다. API 내부 서비스는 API 개발과 관계형 데이터베이스 설계 요구사항 두 개를 추출했고 두 항목을 모두 `SUPPORTED`로 판정했다. 사용량은 Qwen 응답의 `usage`를 합산해 총 2,321토큰이었다. 이 결과는 실행 가능성을 확인한 스모크 테스트이며 정확도나 기업 간 일반화 성능은 아니다.

같은 날 삼성전자, 토스뱅크, 카카오모빌리티 공식 채용 자료에서 직무·자격요건을 발췌해 최대 동시성 4로 다기업 스모크 테스트를 실행했다. 시간은 `time.perf_counter()`로 JD 구조화부터 전체 요구사항 판정 완료까지 측정했고, 토큰은 각 Qwen 응답의 `usage`를 합산했다.

| 기업·직무 | 추출 요구사항 | 부분 실패 | 소요시간 | 총 토큰 | JD·사용자 인용 검증 |
|---|---:|---:|---:|---:|---:|
| 카카오모빌리티 자율주행 개발품질 평가 | 5 | 0 | 24.98초 | 7,689 | 100% |
| 삼성전자 Global Manufacturing & Infra SW | 3 | 0 | 15.82초 | 4,543 | 100% |
| 토스뱅크 ML Backend Engineer | 4 | 0 | 22.73초 | 6,450 | 100% |

첫 실행에서 기술 언어 목록을 모두 충족해야 하는 조건으로 잘못 분해하는 문제와 Qwen JSON 한 건 실패가 확인됐다. 요구사항 추출과 필요 근거 분해를 서로 다른 호출로 분리하고, 대안 목록을 하나의 선택형 근거로 제한했다. JSON Schema에는 역할 8개·근거 3개 상한을 강제하고 요구사항 추출과 판정은 각각 한 번 재시도하도록 보완했다. 표는 수정 후 다시 실행한 결과다.

12개 결과를 1차 내용 검토한 결과 카카오모빌리티의 `기능 및 성능 검증` 한 건은 재검토가 필요하다. 사용자 자료에는 재현 시나리오와 정밀도 지표 작성은 있지만 폐쇄장·실도로 테스트 수행은 명시되지 않았다. 현재 모델의 `SUPPORTED`보다 `PARTIALLY_SUPPORTED`가 타당한 오류 후보이며 사람이 최종 확정하기 전에는 정답 라벨로 사용하지 않는다.

세 직무에서 같은 코드 경로가 실행됐고 인용문 계약도 지켰다는 사실만 확인했다. 정답 요구사항과 정답 연결 라벨이 없으므로 추출 정확도나 직무 간 일반화 성능을 의미하지 않는다.

## 서비스 연동용 고도화

2026-09-13 기준 다음 계약을 추가했다.

- 요구사항별 `suggested_actions`와 `follow_up_questions`
- 사용자 인용문의 정확한 문자 위치
- 공고 출처 메타데이터와 동일 공고의 버전 증가
- 분석 입력·상태·결과·오류의 PostgreSQL 저장
- FastAPI `BackgroundTasks` 기반 비동기 실행과 상태 조회

비동기 작업은 단일 프로세스 MVP용이다. 프로세스가 종료된 뒤 실행 중 작업을 재개하는 큐는 배포 단계에서 별도로 선택한다.

평가셋은 5개 사례, 역할 45개, 연결 55개다. `python -m ai.scripts.summarize_jd_evaluation_dataset`으로 집계했다. 2026-09-13 토스뱅크와 카카오모빌리티 9개 연결을 사용자가 승인해 5개 사례·55개 연결 모두 `HUMAN_APPROVED`다. 평가 코드는 라벨 Accuracy·Macro F1, 필요 근거 Precision·Recall, 존재하지 않는 인용문 비율을 계산한다.

새로 확정한 토스뱅크·카카오모빌리티 9개 연결을 Qwen으로 평가한 결과 Accuracy `0.7778`, Macro F1 `0.7222`, 필요 근거 Precision `0.8667`, Recall `1.0000`, 존재하지 않는 인용문 비율 `0.0000`이었다. 총 토큰은 Qwen 응답 `usage` 합계 10,780이고 연결당 평균 1,197.78토큰이다. 두 오답은 모두 조건을 충족하지 않은 일반 경험을 부분 근거로 인정한 과대 판정이다. 이 결과를 현재 다기업 기준선으로 고정한다.

동일한 관련 섹션·연결 1건 입력 방식으로 5개 사례 55개 연결을 다시 실행한 회귀 결과는 Accuracy `0.9091`, Macro F1 `0.9079`, 필요 근거 Precision `0.9231`, Recall `0.9600`, prediction coverage `0.9818`이다. 총 토큰은 71,730이었다. 55건에는 정책 조정에 사용한 사례가 포함되므로 이 수치는 일반화 성능이 아니라 현재 코드의 회귀 기준이다.

## 다음 작업

빠른 서비스 연동을 우선하므로 같은 검증셋에서 추가 튜닝하지 않는다.

1. 확정된 다기업 평가셋에서 현재 기준선 성능을 측정한다.
2. FastAPI를 실제 실행 환경에 배치하고 백엔드에서 호출한다.
3. 실제 사용자 글을 익명화해 회귀 사례로 축적한다.
4. 여러 JD나 긴 포트폴리오를 함께 처리할 때 검색 단계를 추가한다.

현재의 관련 섹션·단일 조합 `1.0`은 검증셋 튜닝 결과이므로 서비스 성능으로 보고하지 않는다. 새로운 미사용 JD·경험을 사람이 먼저 라벨링한 뒤 일반화 성능을 별도로 측정한다.
