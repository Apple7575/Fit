## 2. 확정된 결정 (뒤집지 마라)

### D-1 · 백엔드 전달 방식 = **파이프라인이 DB에 직접 upsert**

DATA 파이프라인이 `수집 → 정규화 → PostgreSQL upsert`까지 책임진다. 백엔드는 테이블을 **읽기만** 한다.

- 백엔드가 DART API를 직접 호출하지 않는다. (확정 데이터는 연 1회 갱신 · 일 20,000콜 한도 · 사업보고서 원문 8.3MB XML 파싱은 요청 시간 내 불가)
- CSV는 폐기하지 않는다. **적재 전 검증 산출물**로 계속 생성한다(값 CSV + 근거 CSV + 실패 CSV).
- 브랜치 38의 `scripts/load_metrics.py`(upsert, 376행 적재 검증 완료)를 재사용한다.

### D-2 · 스키마 = **develop의 Flyway 스키마 기준 + 근거 테이블만 추가**

- 적재 대상은 `company` · `industry` · `company_metric` · `dart_financial_account` · `dart_employee_status` · `collection_run`. 백엔드 조회 API가 이미 이 테이블들을 읽고 있으므로 **여기가 진짜 적재 대상이다.**
- 브랜치 38의 `company_year`(wide) 구조는 **버린다.** 값은 `company_metric`에 지표 1행씩 넣는다.
- 브랜치 38의 `metric_evidence`(판정·근거) 사상은 **살린다.** `V3__add_metric_evidence.sql` 마이그레이션을 새로 작성해 추가한다. 기존 V1·V2는 **수정 금지**(이미 적용된 마이그레이션을 고치면 Flyway 체크섬이 깨진다).
- `V3`에는 백엔드 코드 수정이 필요한 변경을 넣지 마라. 기존 테이블 `ALTER`가 필요하다고 판단되면 실행하지 말고 보고하라.

## 6. 반드시 지킬 원칙

과거 세션에서 실제로 비싸게 배운 것들이다.

**① 검증 규칙이 파싱 규칙보다 먼저다.**
첫 R&D 시도에서 프로그램은 "성공 5/10"이라고 보고했지만 실제로 맞은 건 1건이었다. SK하이닉스 R&D를 673만원으로 읽었다(실제 6.7조). **실패는 눈에 보이지만 틀린 성공은 안 보인다.** 값을 뽑기 전에 그 값이 맞는지 판정하는 규칙을 먼저 만들어라.

**② 문서만 보고 필드명을 짐작하지 마라.**
평균근속 필드명을 `avrg_cnttk_sdytrn`으로 알고 있었으나 실제는 `avrg_cnwk_sdytrn`이었고, 조용히 `None`이 나왔다. 새 API를 쓸 때는 **응답 원본을 먼저 찍어보라**(`scripts/probe_api.py`).

**③ "회사마다 이름이 다르다"가 거의 모든 실패의 원인이다.**
계정명(`매출액`/`영업수익`), 계정코드, 비율 라벨(`매출액 대비`/`영업수익 대비`), 합계 행 라벨(`성별합계`). **이름으로 찾는 부분은 전부 `config/patterns.yaml`로 뺀다. 커버리지가 안 나오면 코드를 고치지 말고 이 목록을 늘려라.**

**④ 회사가 우리와 다르게 계산한 값은 버리지 말고 기록하라.**
한미반도체는 R&D 비율을 다른 분모로 계산했고, LG전자는 근속을 다른 방식으로 집계했다. 차이를 `gap_pct`에 남겨야 같은 패턴을 나중에 알아챌 수 있다.

**⑤ 근거 없는 숫자는 서비스에서 쓸 수 없다.**
모든 지표에 `verdict` · `source` · `evidence`(접수번호 · 표 순번 · 행 라벨 · 원문 셀)를 남긴다.

**⑥ 수집과 정규화를 절대 합치지 마라.**
수집 계층은 API 호출과 raw 저장만 하고 **해석하지 않는다.** 정규화 계층은 `DartClient`가 아니라 읽기 전용 `RawStore`를 쓴다(계층 분리를 코드로 강제한 것이다). R&D 파서는 5번 고쳤다. 이 구조가 없으면 매번 API를 다시 타야 한다.

```
   corpCode.xml · document.xml 은 zip 을 반환한다. 실패 시엔 XML 에러 문서가 온다.
   → 매직바이트 'PK' 로 구분할 것. 확장자·Content-Type 을 믿지 마라

② fs_div 처리가 API마다 다르다
   fnlttSinglAcnt     응답 행에 fs_div 있음 (연결·별도가 한 응답에 섞임)
   fnlttSinglAcntAll  응답 행에 fs_div 없음 (요청 파라미터일 뿐)
   → 같은 함수로 처리하면 전체재무제표 행이 전부 필터링되어 폴백이 죽는다

③ status 013 은 정상이다
   '조회된 데이터 없음'. 빈 결과로 처리해야 한다
   → 오류로 처리하면 상장 이전 연도에서 파이프라인이 통째로 멈춘다
```

호출 간격은 0.05초(초당 20회)로 3,930콜 연속 성공한 실측이 있다. 인증키는 `python-dotenv`로 `.env`에서 읽는다. **`.env`는 절대 커밋하지 마라**(`.gitignore`에 이미 있다).
