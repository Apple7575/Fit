## 2. v2 에 yoy 파라미터가 없다 — 응답 필드로만 남았다

**이건 명세서에서 읽은 것이 아니라 대조하다 걸린 것이다.** 우리 픽스처에
`metrics_{corpCode}_yoy없이` 가 있었는데, v2 컨트롤러가 이 파라미터를 아예 받지
않는다.

```
CompanyMetricController.getMetrics()   @RequestParam year, keys       ← yoy 없음
CompanyMetricController.getTimeseries() @RequestParam from, to, keys  ← yoy 없음
```

파라미터는 없지만 **응답 필드로는 그대로 있다.** 그리고 Spring 이 모르는
쿼리파라미터를 무시하므로 이렇게 된다.

```
GET /api/companies/00126380/metrics?year=2021&yoy=false
  → 200. yoy 필드가 그대로 실려 온다 (400 이 아니다)
```

즉 **프론트가 옛 파라미터를 계속 보내도 아무 신호가 없다.** 실제로 프론트 문서에
아직 남아 있다.

```
frontend/docs/work-split.md:12   GET /api/companies/{corpCode}/metrics   파라미터: year, yoy
frontend/docs/work-split.md:13   GET /api/companies/{corpCode}/metrics/{metric}   파라미터: year, yoy
```

13행의 개별 조회 경로는 v2 에서 폐기됐고 지금 **404** 다 (`/metrics/revenue`,
`/metrics/revenue/timeseries` 둘 다 확인했다). MVP 미사용이라 화면은 안 깨지지만
표가 사실과 다르다.

**DATA 는 이미 반영했다** — 픽스처의 `yoy없이` 를 `keys지정` 으로 바꿨다.
프론트 문서 두 줄은 백엔드나 프론트 쪽에서 고쳐 주시는 게 맞다고 본다.

참고로 `yoy` 응답 형태는 명세(`docs/design/db-schema.md:221`)와 일치한다 —
`{"prevValue": ..., "changeRate": ...}` 이고 전년 행이 없으면 `null` 이다.
`work-split.md:79` 의 열린 질문("값으로 주는지 비율로 주는지")은 답이 나왔다: 둘 다 준다.

## 3. 비교 기본 7종이 카탈로그 core 6종과 겹치지 않는다 — 결정 요청

98 이 넣은 비교 v2 의 기본 지표는 서비스에 하드코딩돼 있고, 단년 조회의 기본
지표는 카탈로그의 `is_core` 다. 두 목록이 이렇게 다르다.

| 지표 | 단년 조회 (`is_core`) | 비교 (`DEFAULT_METRICS`) |
|---|---|---|
| `revenue` | ○ | ○ |
| `operating_profit` | ○ | ○ |
| `employee_count` | ○ | ○ |
| `average_salary` | ○ | ○ |
| `net_income` | ○ | **×** |
| `average_tenure` | ○ | **×** |
| `revenue_growth` | × (파생) | **○** |
| `operating_margin` | × (파생) | **○** |
| `rd_ratio` | **×** (`is_core = false`) | **○** |

두 가지가 걸린다.

**첫째, `rd_ratio` 의 기본 노출이 화면마다 다르다.** 카탈로그에서 `is_core = false`
라 단년 조회에서는 `keys` 로 명시해야 나오는데, 비교에서는 기본으로 나간다.
V7 이 core/active 를 가른 취지가 "기본 응답에 무엇을 싣나" 였다면 비교가 그 기준을
비켜 간 것이다.

**둘째, `net_income` 이 비교에 없다.** 121 이 방금 47/47 로 적재한 지표다.
단년 조회에는 나가고 비교에는 안 나간다. 넣을지 말지는 화면 기획에 달렸으니
DATA 가 정할 일이 아니라고 본다.

**결정 요청**: (a) `net_income` 을 비교 기본에 넣나, (b) `rd_ratio` 를 비교에서
빼거나 카탈로그의 `is_core` 를 올리나. 둘 다 백엔드 상수 한 줄 또는
마이그레이션 한 줄이다. **DATA 는 어느 쪽이든 대조를 따라 맞춘다** — 지금은
응답에 실린 지표를 그대로 읽어 대조하므로 목록이 바뀌어도 검증은 깨지지 않는다.

## 4. 비교의 파생 2종은 카탈로그를 안 거친다 — 알림

`revenue_growth` 와 `operating_margin` 은 `metric` 테이블에 행이 없다. 자릿수도
카탈로그의 `value_scale` 이 아니라 서비스의 `RATE_SCALE = 1` 하드코딩이다.

```java
case REVENUE_GROWTH  -> changeRate(current.get(REVENUE), previous.get(REVENUE));
case OPERATING_MARGIN -> ratio(current.get(OPERATING_PROFIT), current.get(REVENUE));
default              -> scaled(current.get(metric), scaleByMetric.get(metric));
```

**이건 문제 제기가 아니다.** 단년 조회의 수익성 블록도 같은 구조이고, 저장하면
재적재 때 원본과 어긋난다는 주석의 판단에 동의한다. 다만 결과로 이렇게 된다는
것을 남겨 둔다.

- 카탈로그에서 `value_scale` 을 바꿔도 이 둘은 따라오지 않는다 (두 곳을 고쳐야 한다)
- `metric` 테이블만 보면 이 지표들이 존재하지 않는 것처럼 보인다

`verify_api` 는 백엔드 `changeRate()`·`ratio()` 와 같은 규칙(HALF_UP, 자릿수 1)을
파이썬으로 복제해 DB 에서 계산해 맞댄다. **자릿수 상수가 한쪽만 바뀌면 대조가
깨져서 알려준다** — 그게 지금 우리가 가진 유일한 연동 장치다.

## 5. 후보 목록 API — 검증 범위에 넣나 (결정 요청)

98 의 `GET /api/industries/{industryCode}/companies` 는 아직 probe·verify 범위
밖이다. 넣으려면 probe 케이스와 대조 규칙을 더하면 되는데, 그 전에 하나 짚고 싶다.

**후보 목록은 값이 없는 기업까지 함께 준다.** 정렬이 `revenue` 내림차순이라 값 있는
기업이 위로 오지만, 목록에서 빼지는 않는다.

```
GET /api/industries/26/companies?limit=50
  → 삼성전자 · SK하이닉스 · LG전자 · DB하이텍 · 리노공업  (여기까지 값 있음)
    가온그룹 · 가온칩스 · 경인전자 · 광무 · 광전자 ...     (여기부터 전부 null)
```

지금 적재 규모에서는 KSIC 26 이 5/494, KSIC 58 이 5/281 이다. 목록 아래쪽을 고르면
비교 화면이 전부 빈칸으로 뜬다. `report_gaps` 의 비율 문구도 이번에 이 기준으로
고쳤다 ("응답의 99%" → "후보 목록의 99%").

**결정 요청**: 후보 목록을 값 있는 기업으로 좁히나, 아니면 화면에서 "데이터 없음"을
표시하고 그대로 두나. 전자면 백엔드 쿼리에 `EXISTS (company_metric)` 한 줄이고,
후자면 프론트 처리다. 어느 쪽이든 정해지면 DATA 가 그 규칙으로 대조를 넣겠다.

참고로 파라미터는 `size` 가 아니라 **`limit`** 이다 (검색 API 와 다르다). 기본 50,
상한은 검색과 같다.
