# 0차 실험 — 100개사를 Spark 로 재현한다

**목적은 성능이 아니라 동치 확인이다.** 같은 입력을 Spark 로 돌려 지금 결과와 같은지
본다. 이걸 먼저 하지 않으면, 나중에 기업을 늘렸을 때 결과가 달라져도 Spark 때문인지
파서 때문인지 가릴 수 없다.

- 관련: S15P21A504-73, [SCALE-PLAN](S15P21A504-73-SCALE-PLAN.md) 8장
- 대상: 유니버스 앞 100개사 × 5개년 = 원문 487건 (2.95GB)

---

## 1. 합격 기준

| 산출 | 기준 |
|---|---|
| `segment_revenue` · `facility` · `main_product` · `rd_expense` | **행 집합이 완전히 같아야 한다** |
| `parse_summary` | `seconds` 를 뺀 나머지가 같아야 한다 |
| `passages` | 건수와 문자 수가 같아야 한다 |

파싱은 결정적이다 — 같은 XML 을 같은 패턴으로 읽으므로 다를 이유가 없다. **다르면
그 자체가 버그다.** 행 순서는 보지 않는다(Spark 파티션 순서는 실행마다 다르다).

`company_text` 의 LLM 항목은 0차 대상이 아니다. `generated_at` 이 실행 시각이고
모델 출력이 완전히 결정적이지는 않다.

---

## 2. 준비는 끝나 있다

| 무엇 | 어디 |
|---|---|
| 문서 1건 파싱을 순수 함수로 분리 | `pipeline/business_report/extract.py` `parse_one()` |
| 로컬 실행기가 그 함수를 부르게 | `scripts/parse_business_reports.py` |
| Spark 잡 | `scripts/spark_parse_business_reports.py` |
| 작업 목록 생성 | `scripts/build_spark_jobs.py` |
| HDFS 적재 스크립트 생성 | `scripts/hdfs_put_business_reports.py` |
| 산출 대조 | `scripts/compare_parse_output.py` |

**로컬과 Spark 가 같은 `parse_one` 을 부른다.** 두 경로가 각자 파싱하면 0차의 전제를
확인할 수 없다. XML 해석도 `parse_xml_bytes` 하나를 지난다 — 로컬은 파일을 읽어
넘기고 Spark 는 WebHDFS 로 받은 바이트를 그대로 넘긴다.

리팩터링이 결과를 바꾸지 않았다는 것은 **487건 재파싱으로 확인했다**(3장).

## 4. 클러스터가 서면 — 실행 순서

### ① 원문을 HDFS 로

```bash
# 개발 PC — 무엇을 올릴지 정한다
python scripts/build_spark_jobs.py --companies 100          # _out/spark_jobs.csv (487건)
python scripts/hdfs_put_business_reports.py                 # _out/hdfs_put.sh

# 개발 PC → EC2-A (2.95GB)
rsync -av --include='document_*.xml' --exclude='*' \
      data/.cache/ ubuntu@<EC2-A>:~/br_raw/
scp data/_out/hdfs_put.sh data/_out/spark_jobs.csv ubuntu@<EC2-A>:~/

# EC2-A
bash ~/hdfs_put.sh
hdfs dfs -count /raw/opendart/filings/annual_report      # 487 파일 확인
```

### ② 작업 목록을 Parquet 로

```bash
hdfs dfs -mkdir -p /staged/business_report
spark-submit --master yarn --deploy-mode client \
  -c "from pyspark.sql import SparkSession; s=SparkSession.builder.getOrCreate(); \
      s.read.option('header',True).csv('file:///home/ubuntu/spark_jobs.csv') \
       .write.mode('overwrite').parquet('/staged/business_report/jobs.parquet')"
```

### ③ 파이썬 환경을 워커로

노드가 2대뿐이라 **각 노드에 직접 설치하는 편이 단순하다.**

```bash
# EC2 A · B 양쪽에서
sudo apt-get install -y python3-venv
python3 -m venv ~/brenv
~/brenv/bin/pip install -r requirements.txt        # lxml 은 여기서 6.1.2 로 고정된다

# 두 노드가 같은지 반드시 확인한다
~/brenv/bin/python -c "import lxml.etree as e; print(e.LXML_VERSION, e.LIBXML_VERSION)"
#   기준선: (6, 1, 2, 0) (2, 11, 9)
```

**lxml 버전이 다르면 0차가 성립하지 않는다.** 파손된 마크업을 `recover=True` 로
복구하는 동작이 libxml2 구현에 달려 있어 버전마다 미묘하게 다르다. 표가 하나 더
잡히거나 덜 잡히면 값이 조용히 달라지고, 그러면 차이가 Spark 탓인지 라이브러리
탓인지 못 가린다. `requirements.txt` 가 `lxml==6.1.2` 로 못 박아 두었다.

`--archives` 로 venv 를 보내는 방식도 되지만, 노드 2대에 직접 까는 것이 디버깅이
쉽다. 노드가 늘면 그때 `--archives` 로 바꾼다.

### ④ 파싱

```bash
export WEBHDFS_URL=http://<EC2-A>:9870
export PYSPARK_PYTHON=/home/ubuntu/brenv/bin/python

spark-submit --master yarn --deploy-mode client \
  --conf spark.executor.instances=3 \
  --conf spark.executor.cores=2 \
  --conf spark.executor.memory=2g \
  --conf spark.executor.memoryOverhead=2g \
  scripts/spark_parse_business_reports.py \
    --jobs hdfs:///staged/business_report/jobs.parquet \
    --out  hdfs:///staged/business_report \
    --webhdfs "$WEBHDFS_URL" --slices 24
```

`memoryOverhead=2g` 를 줄이지 마라. 파싱 프로세스가 문서 하나에 약 450MB 를 쓰고
(실측) PySpark 워커는 JVM 밖이라 이 값을 먹는다. 기본값(10%)이면 컨테이너가 OOM 으로
죽는다.

### ⑤ 내려받아 대조

```bash
hdfs dfs -get /staged/business_report ~/spark_out
# Parquet → CSV 로 바꾼 뒤 (또는 대조 도구를 Parquet 리더로 확장)
python scripts/compare_parse_output.py \
    data/staged/business_report ~/spark_out_csv
```

**"전부 동일" 이 나와야 0차 통과다.**

## 5. 다르게 나올 만한 곳 — 미리 적어 둔다

차이가 나면 여기부터 본다.

| 증상 | 의심할 곳 |
|---|---|
| 특정 문서만 `error` | WebHDFS 읽기 실패. 리다이렉트·타임아웃을 본다 |
| 부문 매출이 통째로 `no_external` | 작업 목록의 `external_revenue` 가 비었다. `build_spark_jobs.py` 확인 |
| 숫자가 조금씩 다름 | `patterns.yaml` 이 노드마다 다르다. 코드와 함께 배포됐는지 확인 |
| 행이 몇 개만 빠짐 | 태스크 재시도로 중복 쓰기 후 덮어쓰기. `mode("overwrite")` 와 파티션 확인 |
| 전부 다름 | lxml·libxml2 버전 차이. `requirements.txt` 가 6.1.2 로 고정하지만 libxml2 는 배포판이 준다 — `e.LIBXML_VERSION` 이 (2, 11, 9) 인지 두 노드에서 확인 |

**lxml 버전이 제일 그럴듯한 원인이다.** `requirements.txt` 가 `lxml==6.1.2` 로
고정하지만, 그 안의 **libxml2 는 wheel 에 딸려 오거나 배포판 것을 쓴다.** pip 로 같은
버전을 깔아도 libxml2 가 다를 수 있으니 `LIBXML_VERSION` 까지 대조한다.

## 6. 0차가 끝나면

성능 숫자를 남긴다 — SCALE-PLAN 은 "슬롯 6에서 2.2시간" 으로 **추정**해 뒀고 0차가
그 값을 실측으로 바꾼다.

| 재는 것 | 왜 |
|---|---|
| 전체 소요 | 11,395건 환산의 근거 |
| 태스크당 시간 분포 | 꼬리가 길면 파티션 수를 늘린다 |
| executor OOM 여부 | memoryOverhead 를 다시 잡는 근거 |
| WebHDFS 읽기 시간 비중 | 크면 `binaryFiles` 를 다시 검토할 이유가 된다 |
