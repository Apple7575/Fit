## 2. 확정된 결정

### D-1 · 대상은 타깃 10개사

`config/targets.csv` 기준. 2021~2025년.

`.cache/`와 착지 테이블에는 13개사가 있지만(회귀 기준선용 한미반도체·NAVER·카카오 포함),
**`company_metric`에는 10개사뿐이다.** 커버리지 분모는 10개사로 통일한다.
C(원천 정합성)의 검산은 13개사 원본에 걸 수 있으므로 참고 수치로만 함께 낸다.

### D-2 · API 대조는 **로컬에서 백엔드를 띄워** 한다

스테이징 적재를 기다리지 않는다. Java 21과 `application-local.properties`가 있고,
84가 적재한 로컬 DB(포트 55432)에 6,533행이 들어 있다.

같은 검증 스크립트를 나중에 스테이징에 그대로 재사용할 수 있게 **접속 대상을 설정으로 뺀다.**

### D-3 · 고치지 않는다

이 티켓은 **검증**이다. 발견한 것은 기록하고 보고한다.
데이터 수정 · 파서 개선 · 스키마 변경 · 백엔드 코드 수정은 범위 밖이다.

## 4. 작업 순서

각 Step 끝에서 **무엇을 확인했는지 수치로** 보고하고 멈춰라.

### Step 0 · 로컬 백엔드 기동 확인

여기서 막히면 D-2 를 스테이징 방식으로 전환해야 하므로 먼저 확인한다.

```bash
cd backend
./gradlew bootRun --args='--spring.profiles.active=local'
# datasource 는 54432 가 아니라 84가 쓴 55432 를 가리켜야 한다
```

`application-local.properties`가 `localhost:5432`를 가리키므로 **포트를 덮어써야 한다.**
`localhost`가 아니라 `127.0.0.1`을 쓸 것 (84에서 겪은 IPv6 무한 대기).

- 완료 판정: `GET /api/companies?query=삼성` 이 200 을 반환한다

### Step 1 · API 응답 원본 실측

**명세서를 믿지 말고 실제 응답을 먼저 찍어본다.** (원칙 ②)

엔드포인트 5개 전부:

```
GET /api/companies                                  검색
GET /api/companies/{corpCode}                       기업 상세
GET /api/companies/{corpCode}/metrics               연도별 지표
GET /api/companies/{corpCode}/metrics/timeseries    시계열
GET /api/companies/{corpCode}/industry-comparison   동종업계 비교
```

응답 원본을 `data/tests/fixtures/api/`에 저장한다. 명세와 다른 점이 있으면 **그 자체가 발견 사항**이다.

### Step 2 · DB ↔ API 대조 (`scripts/verify_api.py`)

값만 보지 마라. 아래를 전부 확인한다.

- **값 일치** — `company_metric.metric_value` ↔ 응답의 `value`
- **자릿수** — `NUMERIC(24,4)`가 `metric.value_scale`대로 잘리는가 (금액 0, 근속·비율 1)
- **결측 표현** — 값 없는 지표가 `"value": null` 로 나오는가 (시프트업 2025 `rd_ratio`)
- **비활성 지표** — `rd_cost` 가 응답에 **없어야** 한다
- **상장 이전 연도** — 시프트업 2022 조회 시 동작
- **파생 필드** — `market` (`corp_cls` Y→KOSPI), `yoy.changeRate` 계산
- **정렬·개수** — 동종업계 비교의 순서와 노출 개수

### Step 3 · 누락 사유 분류 (`B`)

지금 커버리지 리포트는 확보율만 보여준다. **없는 것의 사유를 나눈다.**

```
① 미상장        listed_from 이전       정상. 결측이 아니다
② rejected      의도적으로 버림         단위 미상 등
③ not_found     못 찾음               파서 한계
④ 수집 실패      API 오류              재시도 대상 (현재 0건)
```

**④와 ①을 섞으면 커버리지가 왜곡된다.** 지표 × 연도 × 사유 격자로 낸다.

### Step 4 · 원천 정합성 검산 확대 (`C`)

84는 검산 축이 하나뿐이었다 — 상세 행 합 = 합계 행. **62건 중 14건에만 적용됐다.**
합계 행이 없어도 쓸 수 있는 축을 추가한다.

| 축 | 방법 | 적용 가능 범위 |
|---|---|---|
| 급여 교차 | `fyer_salary_totamt ÷ sm` vs `jan_salary_am` | 두 값이 다 있는 행 |
| 전년 대비 급변 | 매출·인원이 비정상적으로 튀는가 | 2년 이상 있는 기업 |
| 지표 간 모순 | `avg_salary × employee_count` ≈ 연간급여총액 | 대부분 |
| 착지 ↔ 지표 | `dart_employee_status.sm` 합 vs `employee_count` | 전체 |

**목표를 수치로 낸다**: 검산 가능 건수를 14/62 에서 몇 건까지 올렸는가.

발견한 불일치는 **오류로 단정하지 마라.** 회사가 다르게 계산한 것일 수 있다
(`DESIGN.md` 4-5장: 한미반도체 R&D 분모 · LG전자 근속 · 크래프톤 급여 12%).
`metric_evidence.gap_pct` 에 이미 기록되는 값과 대조하라.

### Step 5 · 통합과 문서 (`D`)

- Step 2~4 의 검사를 `verify_db.py` 에 합치거나 `verify_all.py` 로 묶는다
- 실패 시 종료코드 1 (기존과 동일)
- `Jenkinsfile` 의 Verify 단계 연동 여부는 **판단해서 제안**하라. DB 의존이 생기므로 장단이 있다
- `HANDOFF.md` 갱신 · `BACKLOG_STATUS.md` 의 F-30 을 완료로

## 5. 84에서 이관된 것 — 반드시 다룰 것

### ① 엔씨소프트 2024 원천 데이터 오류

`연구개발/남`이 두 번 나오고 두 번째 행(840명)은 성별이 `여`여야 한다. 합계 행으로 검산하면 명백하다.

```
남 상세 합  104 + 505 + 1,968 = 2,577  = 성별합계 남
여 상세 합   49 + 366 +   840 = 1,255  = 성별합계 여
```

UNIQUE 키로 두 행을 구분할 수 없어 착지 테이블에서 840명이 빠져 있다.
**지표 값에는 영향이 없다** — 정규화는 캐시를 직접 읽고 상세 행을 전부 더한다.

→ 정식으로 기록하고, **같은 유형이 더 있는지 찾아라.**

### ② 검증 범위가 좁다

상세 행 ↔ 합계 행 대조가 62건 중 14건에만 적용된다. → Step 4.

### ③ API 노출값 대조

→ Step 1~2.
