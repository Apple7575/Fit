취준생용 기업분석 서비스의 데이터 산출물을 만든다. DB에 적재 가능한 최종 CSV 2개를 생성하는 것이 완료 조건.

**MVP 지표 6종**

| 지표 | 기간 |
|---|---|
| 매출액, 영업이익 | 5년 (2021~2025) |
| 직원수, 1인 평균급여, 평균 근속연수 | 5년 |
| R&D / 매출 | 5년 |

**대상 기업 10개** — KSIC 중분류 2개 안에서 선정 (`config/targets.csv`)

| KSIC | 업종명 | 기업 |
|---|---|---|
| 26 | 전자 부품, 컴퓨터, 영상, 음향 및 통신장비 제조업 | 삼성전자, SK하이닉스, LG전자, DB하이텍, 리노공업 |
| 58 | 출판업 (소프트웨어 개발·공급 포함) | 크래프톤, 엔씨소프트, 넷마블, NHN, 시프트업 |

## 2. 확정된 의사결정

| # | 결정 | 근거 (실측) |
|---|---|---|
| 1 | **연결(CFS) 우선, 없으면 별도(OFS).** 어느 기준을 썼는지 `fs_div`에 기록 | 삼성전자 2025 매출 CFS 333.6조 vs OFS 238.0조. 95조 차이. 뉴스·증권가가 연결 기준 |
| 2 | **5년치는 연도별 5회 호출, 당기(thstrm)만 사용** | 1회 응답에 당기·전기·전전기 3년이 오지만, 10개사면 50콜이라 단순성 우선. 나중에 2회 호출로 전환 가능하도록 `source_year` 컬럼 유지 |
| 3 | **표는 `company` + `company_year` 2개** | 기업명·업종은 연도와 무관하므로 반복 저장하지 않음 |
| 4 | **사업보고서 원문은 1콜.** `list.json` 불필요 | 재무 API 응답에 `rcept_no`가 이미 포함됨. 그 접수번호로 `document.xml`이 정상 열림을 확인 |
| 5 | **업종은 통계청 KSIC 중분류 2자리** | 임의 그룹핑은 서비스에서 근거로 쓸 수 없음. DART `induty_code`가 KSIC 코드 |
| 6 | **타깃 선정도 KSIC 코드 기준** | 코드를 먼저 정하고 그 안에서 기업을 뽑아야 공식 기준상 한 그룹이 됨 |
| 7 | **`corp_name`(DART 등록명)과 `display_name`(표시용) 분리** | 엔씨소프트의 DART 등록명은 `(주)엔씨`. 그대로 쓰면 사용자가 못 찾음 |
| 8 | **원본 응답은 전부 파일로 캐시** | 파싱 규칙을 수십 번 고치게 되므로, 재실행 시 API를 다시 때리면 안 됨 |
| 9 | **모든 지표는 다경로 + 교차검증** | 단일 경로는 조용히 틀린다. 아래 4장 참고 |
| 10 | **파생지표 "1인당 매출"은 만들지 않는다** | 매출은 연결(자회사 포함), 직원수는 별도(본사)라 분자·분모 기준이 다름. 삼성전자 12.9만명은 국내 법인만 |

### 폐기된 접근

- **KSIC 코드로 업종을 자동 판별** — 반도체 5개사가 4개 그룹으로 흩어짐. 삼성전자는 `264`(통신·방송장비), 한미반도체는 `29271`(기계). 지주회사·복합기업 문제도 여기서 발생. 10개사 규모에서는 KSIC 중분류로 묶고 타깃을 그 안에서 뽑는 편이 정확
- **`is_target` / 피어 유니버스 컬럼** — 타깃 10개사가 곧 비교 그룹이므로 불필요
- **`account_id`(XBRL 표준코드) 단독 사용** — 표준대로 태깅되지 않는 회사가 있음 (4장 참고)

## 4. 실제로 부딪힌 문제와 대응

이 장이 이 문서의 핵심이다. **네 지표 모두 근본 원인이 같았다 — "회사마다 이름과 구조가 다르다."**

### 4-1. 매출액: 이름으로도, 코드로도 단독으로는 실패한다

**문제**

```
카카오 2021 주요계정 응답 (28행)
  IS  영업이익 / 법인세차감전순이익 / 당기순이익 / 총포괄손익
  → 매출 행이 없음. 같은 회사 2023년 응답에는 있음

전체재무제표에서 찾으면
  account_nm = '영업수익'  5.91조
  account_id = 'ifrs-full_GrossProfit'   ← 매출총이익 태그를 달아놓음
크래프톤은  account_id = '-표준계정코드 미사용-'
넷마블 2023~25 전체재무제표  account_nm = 'Ⅰ.영업수익'   ← 번호 접두사
```

주요계정 API는 XBRL 표준 태그로 계정을 골라내므로, **태깅이 표준과 다르면 매출 행 자체가 응답에서 빠진다.**

**대응 — 3경로 + 교차검증**

| 경로 | 방법 | 실측 성공률 |
|---|---|---|
| A | 주요계정 + 계정명 (표준화된 이름) | 46/50 |
| B | 전체재무제표 + `account_id` | 46/50 |
| C | 전체재무제표 + 계정명 (접두사 정규화 후) | **50/50** |
| — | **합집합** | **50/50, 겹치는 43건 값 불일치 0건** |

- 채택 우선순위 **A → B → C**
- 판정: 경로 2개 이상 값 일치(오차 0.5% 이내) → `verified`, 불일치 → `conflict`, 1개뿐 → `single_source`
- **실측 결과: `verified` 50/50, `conflict` 0건**

**구현 규칙**

```
계정명 후보 (정확일치, 우선순위 순)
  매출액 → 영업수익 → 수익(매출액) → 영업수익(매출액) → 매출 → 수익

제외 정규식 ('수익'이 들어가지만 매출이 아닌 것)
  기타수익|금융수익|이자수익|배당금수익|임대수익|수수료수익|외환|처분이익|
  평가이익|지분법|법인세|영업외|중단영업|매출원가|매출총이익|매출채권|미수

계정코드 후보
  ifrs-full_Revenue, ifrs_Revenue,
  ifrs-full_RevenueFromContractsWithCustomers,
  ifrs-full_RevenueFromContractsWithCustomersRecognisedAtPointInTime

계정명 정규화 (전체재무제표는 회사 원문이므로 필수)
  ^[ⅠⅡⅢⅣⅤⅥⅦⅧⅨⅩIVX0-9]+\s*[.．)\]]\s*  →  제거
```

**주의 — `fs_div` 처리가 API마다 다르다**

```
주요계정        응답 행에 fs_div 있음      → 행별로 CFS/OFS 필터링
전체재무제표     응답 행에 fs_div 없음      → 요청 시 지정했으므로 그대로 통과
```

이걸 같은 함수로 처리하면서 "행의 `fs_div`가 CFS가 아니면 건너뛴다"고 쓰면, 전체재무제표 행이 전부 걸러진다. **실제로 이 버그로 폴백이 작동하지 않았다.**

### 4-2. R&D: 파싱 규칙보다 검증 규칙이 먼저다

**첫 시도의 실패** — 프로그램은 "성공 5/10"이라고 보고했지만 실제로 맞은 건 1건이었다.

```
SK하이닉스   6,732,527원 (673만원)   실제 6.7조    ← 단위 '백만원'을 못 읽음
엔씨소프트   325,174,401원 (3.25억)  실제 3,252억
보고비율 8건이 100.0                              ← 라벨의 '×100'을 값으로 읽음
```

**실패는 눈에 보이지만 틀린 성공은 안 보인다.** 검증 규칙이 없으면 실패율 자체를 측정할 수 없다.

**원인 4개와 대응**

| 원인 | 대응 |
|---|---|
| 단위가 표 앞 문장이 아니라 **직전의 1행 1열 표**에 있음 (50건 중 44건이 이 형태) | 자기 표 + 직전 표 3개까지 거슬러 올라가 `단위` 탐색. 찾은 위치를 기록 |
| 라벨 안의 숫자를 값으로 읽음 (`...÷당기매출액×100]`) | **숫자 전용 셀만** 값으로 인정: `^[\d,.\s%()▲△\-–]+$` |
| 재무제표 주석의 9,684행 표를 후보로 선택 | 후보를 **섹션 제목에 '연구개발'이 있는 표**로 제한 |
| 라벨 조건이 느슨함 (`합계`/`계`/`비율` 단독 허용) | `연구개발비`가 포함된 라벨만. `회계처리`/`무형자산`/`판매비`/`제조경비`/`정부보조` 행 제외 |

**대응 — 3경로 + 교차검증**

| 경로 | 방법 | 실측 확보 |
|---|---|---|
| ① 표내부 | 같은 표의 `연구개발비 합계` ÷ 같은 표의 `매출액`. 단위를 몰라도 비율은 정확 | 1/50 (표에 매출액을 같이 적는 회사는 드묾) |
| ② 외부계산 | 파싱한 R&D 금액 ÷ 재무 API 매출액 | 50/50 |
| ③ 보고값 | 보고서가 직접 적어놓은 비율 | 50/50 |

- 판정: 2개 이상이 **±0.5%p** 이내 → `high` / 불일치 → `mismatch`(버림) / 1개뿐 → `unverified` / 단위 불명 → `no_unit`(버림) / 표 없음 → `not_found`
- **실측 결과: `high` 50/50** (10개사 × 5년, 기존 검증 대상 기준)
- 허용범위 근거: `high` 41건 중 최대 오차가 엔씨소프트 0.43%p. 보고서가 비율을 정수로 반올림해 적기 때문(계산 21.58% → 보고 `22%`). **0.5%p는 이 분포를 보고 정한 값**

**구현 규칙**

```
섹션 제목        '연구개발'  포함
금액 행 라벨      연구개발비용?(합계|총계|계)
                + 표 안에 '연구개발비'가 있으면 '합계' 단독도 인정 (시프트업)
비율 행 라벨      연구개발비.{0,20}(매출액|영업수익|매출|수익).{0,10}(비율|대비)
                | (매출액|영업수익|매출)대비.{0,10}연구개발
표내 매출 라벨    매출액 | 영업수익 | 수익(매출액) | 매출
제외 라벨        회계처리|무형자산|판매비|제조경비|정부보조|정부출연
단위             백만원=10^6, 천원=10^3, 억원=10^8, 원=1
```

**비율 라벨의 분모 이름도 회사마다 다르다** — 삼성전자 `연구개발비 / 매출액 비율`, NAVER `연구개발비/영업수익 비율`. 이것 때문에 NAVER 5건이 검증 실패 상태였다.

**열 선택 — 연결/별도가 한 표에 섞인다 (50건 중 10건)**

```
NAVER 2021 (5열)          과 목 | 연결 | 연결 | 별도 | 별도
                                | 제23기 | 제22기 | 제23기 | 제22기
카카오 2021 (8열)          과목 | 연결×3 | 별도×3
```

"라벨 뒤 첫 숫자" 규칙은 연결이 먼저 와서 우연히 맞았을 뿐이다. **별도를 먼저 적는 회사에서는 조용히 틀린다.** → 헤더 3행에서 `연결`/`별도` 열 번호를 찾아, 둘 다 있으면 연결 열을 우선한다.

**열 인덱스를 고정하면 안 된다** — `COLSPAN`/`ROWSPAN` 때문에 논리 격자가 행마다 어긋난다. 라벨 뒤 첫 숫자(연결 열 우선)를 쓴다.

### 4-3. 직원: 행 단위가 아니라 필드 단위로 판단해야 한다

**문제 — 삼성전자는 급여를 상세 행에 안 적고 합계 행에만 적는다**

```
삼성전자 2025 (6행)
  DX/남      38,119명  근속 17.4  급여 '-'
  DX/여      12,698명  근속 14.4  급여 '-'
  DS/남      56,154명  근속 11.7  급여 '-'
  DS/여      21,910명  근속 12.1  급여 '-'
  성별합계/남  94,273명  근속 14.0  급여 1.67억   ← 급여가 여기만 있음
  성별합계/여  34,608명  근속 13.0  급여 1.30억
```

"합계 행은 제외"라는 행 단위 규칙은 직원수 2배 계산은 막았지만, **급여가 있는 유일한 행을 버렸다.** (삼성전자 5년 전부 급여 결측)

**대응 — 필드별 소스 분리**

```
직원수     상세 행만 (합계 행 제외)                    합계 행을 더하면 2배
평균근속   상세 행 인원 가중평균                        합계 행에도 있어 대조 가능
1인평균급여 상세 행 → 없으면 합계 행에서 가중평균          삼성전자·LG전자 케이스
```

- 합계 행 라벨: `^(성별)?(합계|총계|계)$|^전체$` — **`성별합계`라는 표기를 쓴다**
- `fo_bbm`에 앞뒤 공백이 붙는 회사가 있다(엔씨소프트 `' 전사 '`) → 공백 정리 필수
- `sm`(합계)이 없으면 `rgllbr_co`(정규직) + `cnttk_co`(계약직)로 대체
- 근속 표기 정규화: `12.3` / `8년 6개월` / 개월 수를 그대로 적은 경우

**자체 검증 — 합계 행 대조**

```
삼성전자 2025
  인원  상세 합 128,881  =  합계 행 128,881    ✓
  근속  상세 계산 13.72년  =  합계 행 13.73년    ✓
```

합계 행이 있는 9건 전부 인원이 일치했다. 집계 로직이 맞다는 독립적 증거.

**실측 결과: 직원수 50/50, 근속 50/50, 급여 50/50, 경고 0건**

### 4-4. 사업부문(`fo_bbm`)은 시계열로 쓸 수 없다

```
삼성전자    2021  CE / IM / DS / 기타      →  2022  DX / DS  (CE+IM 통합)
엔씨소프트   2021  관리사무직 / 연구개발
           2023  IT·플랫폼 / 사업·경영관리 / 연구개발
           2025  전사                      (아예 합쳐버림)
```

- **8/10 회사는 사업부문이 1개뿐**이다 (`전사`, `반도체`, `게임` 등)
- 쪼개는 회사도 연도마다 구분이 바뀌어 **부문별 인원 추이를 만들 수 없다**
- 같은 필드에 다른 개념이 들어온다 — 삼성전자는 **사업**(DX/DS), 엔씨소프트는 **직군**(관리사무직/연구개발). 회사 간 비교도 불가능
- 세부 사업부(MX, 메모리, 파운드리 등)는 공시 의무가 없어 나오지 않는다

→ **회사 총계만 시계열 지표로 쓴다.** 원본은 raw에 남겨두고, 사업부문 정보는 나중에 "있는 회사만 보여주는 부가 정보"로 활용.

### 4-5. 회사가 우리와 다른 방식으로 계산한 값 — 버리지 않고 기록한다

```
한미반도체 2021  우리 계산 R&D 216억 ÷ 매출 3,732억 = 5.78%
                보고서에 적힌 비율 5.6%          (반올림해도 5.8%여야 함)
                → API 3경로는 소수점까지 일치. 회사가 다른 분모를 쓴 것

LG전자 2022    상세 근속 가중평균 12.75년  vs  합계 행 13.3년
                인원은 29,601명으로 정확히 일치. 회사가 근속을 다르게 계산

크래프톤       보고된 1인평균급여  vs  (연간급여총액 ÷ 인원)  차이 12% (지속적)
                스톡보상·중도 입퇴사자 포함 기준 차이로 추정
```

이런 차이는 **파싱 오류가 아니라 회사의 기재 방식 차이**다. 값을 버리지 말고 `*_gap_pct` 컬럼에 기록해서, 같은 패턴이 다른 회사에서 나오면 알아챌 수 있게 한다.

**R&D 역산 검증의 위치** — R&D 표의 `금액 ÷ 보고비율`로 매출을 역산해 대조할 수 있다(추가 호출 0). 그러나 회사가 어떤 분모를 썼는지 모르므로 **API 경로가 2개 이상이면 판정에서 제외하고 참고만 하고, API 경로가 1개뿐일 때만 대조 상대로 쓴다.** 허용오차는 보고비율의 표기 자릿수에서 계산한다(`19%` → ±0.5%p → 역산 매출 ±2.6% 허용 / `18.5%` → ±0.27%).

### `company` — 기업 마스터 (기업당 1행)

| 컬럼 | 예시 | 설명 |
|---|---|---|
| `corp_code` | `00126380` | **PK.** DART 고유번호 8자리 |
| `corp_name` | `삼성전자(주)` | DART 등록명 |
| `display_name` | `삼성전자` | 화면 표시용 |
| `stock_code` | `005930` | 종목코드 |
| `induty_code` | `264` | DART 원본 KSIC (3~5자리 혼재) |
| `ksic_division` | `26` | **KSIC 중분류 2자리. 비교 그룹의 기준** |
| `division_name` | `전자 부품, 컴퓨터, ...` | 중분류 명칭 |
| `listed_from` | `2024` | 상장연도. 이전 연도 결측은 "수집 실패"가 아님 (시프트업) |

### `company_year` — 기업-연도 지표 (값)

지표를 컬럼으로 펼친 **wide 구조**. `PK = (corp_code, bsns_year)`.

> 백로그 F-07·F-13·F-27의 "기업·연도·지표" 표현은 지표를 행으로 두는 long 구조를 뜻하는 것이 아니라 관용적 표현임을 팀 확인 완료(2026-08-27). **wide로 확정.**

| 컬럼 | 설명 |
|---|---|
| `corp_code` + `bsns_year` | **복합 PK.** 중복 행 방어 |
| `revenue`, `operating_profit` | 원 |
| `fs_div` | `CFS`/`OFS` — 어느 기준을 썼나 |
| `employee_count`, `regular_count`, `contract_count` | 명 |
| `avg_salary_krw` | 원 |
| `avg_tenure_years` | 년 |
| `rnd_cost_krw`, `rnd_ratio_pct` | 원 / % |
| `rcept_no`, `source_year` | 근거 공시 / 어느 보고서에서 뽑았나 |

### `metric_evidence` — 지표별 근거·판정

값 테이블에 근거 컬럼을 다 넣으면 6지표에 컬럼 20개가 되고, 지표를 추가할 때마다 `ALTER TABLE`이 필요하다. **값은 wide, 근거는 지표별 1행**으로 분리한다. 지표가 늘어도 스키마 변경이 없다.

| 컬럼 | 예시 | 설명 |
|---|---|---|
| `corp_code` + `bsns_year` + `metric_code` | `00126380`, `2025`, `rnd_ratio_pct` | **복합 PK** |
| `verdict` | `verified` | `verified`/`unverified`/`rejected`/`not_found` |
| `source` | `doc_table` | `A_major_name`/`B_full_id`/`C_full_name`/`detail`/`total_rows`/`doc_table` |
| `gap_pct` | `3.18` | 회사 기재값과의 차이 (4-5장. 한미반도체·LG전자·크래프톤 케이스) |
| `evidence` | `{"rcept_no":"...","table_idx":110,"row_label":"연구개발비용 계","raw":"37,754,800"}` | JSONB |

웹은 `company_year`만 조인 없이 조회한다. `metric_evidence`는 데이터 검수와 F-30 정합성 검증에서만 쓴다.

**근거 없는 숫자는 서비스에서 쓸 수 없다.** 값보다 추적성이 먼저다.

## 6. 파이프라인 구조

```
[1] 수집     API 호출 → 응답 원본을 파일로 저장 (data/raw/)
              여기서는 해석하지 않는다. 받은 그대로 저장
                ↓
[2] 정규화    원본 → 기업-연도 1행
              계정명 매칭, 직원 행 집계, 단위 환산, 교차검증이 전부 여기
                ↓
[3] 산출     표 합치기 + 파생값 → CSV 2개
                ↓
[4] 적재     PostgreSQL
```

**[1]과 [2]를 분리하는 것이 설계의 핵심이다.** 파싱 규칙을 고쳤을 때 API를 다시 호출하지 않고 [2]만 재실행할 수 있다. R&D 파서는 이번 작업에서 5번 고쳤고, 그때마다 원본을 다시 받았다면 작업이 불가능했다.

**raw 레이아웃** (파일명으로 무엇의 원본인지 알 수 있게)

```
data/.cache/CORPCODE.xml
data/.cache/company_<corp_code>.json
data/.cache/fnlttSinglAcnt_<corp_code>_<year>.json
data/.cache/fnlttSinglAcntAll_<corp_code>_<year>_<fs_div>.json
data/.cache/empSttus_<corp_code>_<year>.json
data/.cache/document_<rcept_no>.xml
```

> 이 문서는 처음에 위 경로를 `data/raw/` 로 적어 두었으나 구현은 `data/.cache/` 를 쓴다
> (`pipeline/paths.py` 의 `cache_dir()`, 환경변수 `DART_CACHE_DIR`). 실제 경로로 고쳤다.
> `data/raw/opendart/` 로 옮기는 것이 앞으로의 기준이며 그 판단과 미룬 이유는
> [`DATA_STORAGE_STANDARD.md`](DATA_STORAGE_STANDARD.md) 2장에 있다. 저장 위치·파일명·Git
> 추적 범위의 정본은 그 문서다.

**설정 파일** — 이름으로 찾는 부분은 전부 설정으로 뺀다. 커버리지가 안 나오면 **코드를 고치지 말고 후보 목록을 늘리는 것이 원칙.**

```
config/targets.csv       타깃 10개사 + KSIC 중분류 + 상장연도
config/patterns.yaml     계정명 후보/제외, R&D 라벨, 단위, 합계 행 라벨
```

**사업보고서 XML 파싱 주의사항**

- 인코딩: 선언은 `utf-8`인데 실제로 다른 문서가 섞임 → 인코딩 추정 + `recover=True`
- 마크업이 깨져 표가 안 닫히고 뒤 내용을 삼키는 경우가 있다 (시프트업 2025: 4,937행 병합 표) → **후보 표에 행 수 상한(30행 정도)을 걸어야 한다**
- 표마다 `(문서 내 순번, 직전 TITLE, 직전 텍스트)`를 함께 보관 → 증거 추적 및 단위 탐색에 필요

## 8. 미해결 / 남은 위험

| # | 항목 | 상태 | 대응 방향 |
|---|---|---|---|
| 1 | 시프트업 R&D 금액 행 라벨이 `합계` 단독 | 미해결 | 표 안에 '연구개발비'가 있으면 `합계` 단독도 인정 (표 단위 컨텍스트) |
| 2 | 시프트업 2025 문서에 4,937행 병합 표 | 미해결 | 후보 표에 행 수 상한(30행) + 비율 행·합계 행이 함께 있는 작은 표 우선 |
| 3 | 연결/별도 열 순서 의존 | **해결** (헤더 기반 선택) | 50건 중 10건이 혼재 구조였음 |
| 4 | 다른 업종 미검증 | 미검증 | 지금은 KSIC 26·58만. 제약(21)·금융(64·66)은 표 형식과 계정명이 다를 가능성 |
| 5 | `unverified` 등급의 서비스 노출 정책 | 미정 | 값은 DB에 넣되 화면 표시 여부를 결정해야 함 |
| 6 | 사업부문별 지표 | 보류 | 4-4 참고. 원본만 보관 |

**등급 이름** — 초기에 `high`/`medium`을 썼으나 `medium`이 "중간 품질"로 읽히는 문제가 있다. 실제 의미는 "미검증"이므로 아래 이름을 권장한다.

```
verified     교차검증 통과 (경로 2개 이상 일치)
unverified   근거 1개, 대조 불가 — 값이 틀렸다는 뜻이 아니라 확인할 방법이 없다는 뜻
rejected     경로 간 불일치 → 버림
no_unit      단위 불명 → 버림
not_found    표/데이터 없음 (해당 없음과 구분할 것)
```

## 9. 작업 순서 제안

1. `config/patterns.yaml` 작성 — 4장의 후보 목록·정규식 전부
2. 수집 계층 (`collect`) — API별 함수 + raw 캐시. 해석하지 않음
3. 정규화 계층 — 매출(3경로) / 직원(필드별 집계) / R&D(3경로) 각각 독립 모듈
4. 산출 계층 — `company`, `company_year` CSV + PK 중복·필수 컬럼 검사
5. 8장 1·2번(시프트업 케이스) 반영 후 15건 재검증
6. 다른 업종 1~2개사로 확장 테스트 (제약 또는 금융)
