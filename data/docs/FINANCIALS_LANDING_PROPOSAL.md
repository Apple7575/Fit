## 0. 아주 쉽게 — 이게 무슨 일인가

**한 문장:** 회사 2,703곳이 5년 동안 낸 성적표에서 **숫자만** 뽑아다가, 상자 세 개에 나눠 담았다.

### ① 성적표 도서관

우리나라 회사들은 1년에 한 번 **사업보고서**라는 아주 두꺼운 성적표를 냅니다.
그 성적표를 전부 모아두는 나라의 큰 도서관이 **DART** 입니다.

성적표에는 두 가지가 섞여 있습니다.

```
글로 쓴 것    "우리는 반도체를 만들고, 앞으로 이런 걸 할 거예요"   ← 팀장님이 맡음
숫자로 쓴 것  "매출 4조, 이익 3천억, 빚 2조"                      ← 제가 맡음
```

글은 사람 말이라 컴퓨터가 읽기 어려워서 **AI 가 읽어야** 합니다. 시간도 돈도 많이 듭니다.
그런데 **숫자는 도서관이 이미 표로 정리해서 따로 줍니다.** 공짜로, 정확하게요.

그래서 팀장님이 이렇게 나누자고 하셨습니다. **"글은 내가 AI로 읽을 테니, 숫자는 표로 받아와라."**
같은 숫자를 AI 로 또 읽으면 시간과 돈만 두 번 쓰니까요.

### ② 2,703곳이 어디서 나온 숫자인가

우리가 가진 회사 명단은 **3,930곳**입니다. 여기서 진짜 주식시장에 올라와 있는 회사만 세면
**2,703곳**입니다. 팀장님이 말씀하신 "4천 중 2천7백"이 정확히 이것이었습니다.

```
코스피    829
코스닥  1,768
코넥스    106      합계 2,703
그 외   1,227      ← 시장에 없어서 뺌
```

### ③ 한 명씩 물어보면 너무 오래 걸린다

도서관에 숫자를 달라고 할 때, 원래는 **회사 하나씩** 물어봐야 합니다.

```
회사 2,703곳 × 5년 = 13,515번 물어봐야 함
그런데 도서관은 하루에 20,000번만 대답해 줍니다  →  하루치의 68%를 다 씀
```

그런데 찾아보니 **"100곳씩 한꺼번에 물어보는 창구"** 가 따로 있었습니다.

```
100곳씩 묶으면 28묶음 × 5년 = 140번
13,515번  →  140번    (96배 줄었습니다)
```

**하지만 그 창구를 한 번도 써본 적이 없어서**, 진짜 100곳까지 되는지, 중간에 한 곳이
없으면 나머지도 다 날아가는 건 아닌지 **먼저 시험해 봤습니다.** 결과는 4장에 있습니다.

### ④ 받아온 걸 상자 세 개에 나눠 담았다

이건 우리 팀이 이미 정해 둔 규칙입니다 ([`DATA_STORAGE_STANDARD.md`](DATA_STORAGE_STANDARD.md)).

```
1번 상자 · 원본     도서관이 준 그대로. 절대 손대지 않는다.   179MB
                    → 나중에 "우리가 값을 잘못 고친 거 아냐?" 할 때 여기를 봅니다

2번 상자 · 정리     글자로 된 "4,041,639,278" 을 숫자로 바꾸고
                    이상한 것에 표시를 붙인 것                47MB

3번 상자 · 완성     회사별·연도별로 표를 예쁘게 편 것.
                    이대로 DB 에 넣을 수 있습니다             5.6MB
```

**왜 굳이 셋으로 나누냐면**, 나중에 숫자가 이상할 때 *도서관이 이상하게 준 건지*
*우리가 정리하다 실수한 건지* 를 구분할 수 있어야 하기 때문입니다.
한 상자에 다 섞어 담으면 영영 알 수 없게 됩니다.

### ⑤ 답이 맞는지 스스로 채점해 봤다

숫자를 받아만 놓고 "잘 됐어요" 하면 안 됩니다. **채점하는 방법**을 하나 찾았습니다.

성적표에는 올해 숫자만 있는 게 아니라 **작년 숫자도 같이** 적혀 있습니다. 그러면:

```
2023년 성적표에 적힌 "작년 매출"      =    2022년 성적표에 적힌 "올해 매출"
```

이 둘은 같아야 합니다. 같은 숫자를 서로 다른 종이에서 두 번 받는 셈이니까요.
**22만 쌍을 맞춰봤더니 94.7%가 같았습니다.**

나머지 5.3%는 왜 다를까요? **회사가 나중에 작년 숫자를 고쳐 적었기** 때문입니다.
잘못이 아니라 회계에서 정상적으로 일어나는 일입니다. 다만 **우리가 둘 중 뭘 저장할지**
정해야 해서, 6장에 판단 요청으로 올려 두었습니다.

### ⑥ 그래서 지금 부탁드리는 것

받아온 숫자를 **DB 에 넣을 방(테이블)이 아직 없습니다.**
방을 만드는 일은 백엔드 담당이라(팀 규칙 D-6), 제가 만들지 않고 **설계도만 그려서** 드립니다.

이 문서가 그 설계도입니다. 5장이 설계도이고, 6장이 **같이 정해야 할 것**입니다.

## 1. 무엇을 넣으려는가

DART 정기보고서 재무정보의 **다중회사 주요계정**(`fnlttMultiAcnt`).
상장사 2,703개사 × 2021~2025년을 수집·정규화까지 마쳤다.

```
수집   140콜 · 오류 0 · 314,655행 · 179MB
       한 해라도 응답한 회사 2,599/2,703 (96.2%)
정규화 293,332행 (중복 21,323행 접음) · 회사 2,599
정리본 21,397행 (회사 × 연도 × 연결/별도) · 14개 계정
검산   verify_all.py 의 [6] 으로 편입. 축 5개 · DB·API 불필요
       F-1 자산 = 부채 + 자본   21,322/21,326 (99.98%)   모순 판정 축
       F-3 연도 교차          212,339/224,323 (94.66%)  차이 판정 축
```

**검산에서 원천 오류 4건이 나왔다.** 그중 둘은 자산총계 한 값만 틀렸다는 것이
두 독립 합의 일치로 확정되어 `known_findings.yaml` 에 등록했고(우리기술투자 2025 ·
신영스팩10호 2024), 나머지 둘(세종메디칼 2023 · 에스티팜 2022)은 **원인을 몰라
등록하지 않았다 — 조사 대상이다.** 그래서 `verify_all.py` 는 지금 종료코드 1 이다.

## 2. 왜 `fnlttSinglAcntAll` 이 아니라 `fnlttMultiAcnt` 인가

| | 호출 수 | 일 한도 대비 |
|---|---|---|
| `fnlttSinglAcnt` 단건 | 2,703 × 5 = **13,515콜** | 68% |
| `fnlttSinglAcntAll` 단건 × 연결·별도 | 2,703 × 5 × 2 = **27,030콜** | **초과** |
| `fnlttMultiAcnt` 100개사 묶음 | 28 × 5 = **140콜** | 0.7% |

전체 재무제표(`SinglAcntAll`, 회사당 234~265행 + `account_id`)는 하루에 끝나지 않는다.
지금 화면·API 가 쓰는 지표(매출액·영업이익·당기순이익·부채총계·자본총계)는 **전부 주요계정에
들어 있으므로** 주요계정으로 먼저 뚫고, 전체 재무제표는 필요한 계정이 드러난 뒤에 따로 판단한다.

## 4. 엔드포인트 실측 — 명세가 아니라 잰 값이다

`scripts/probe_multi_acnt.py` · 2026-09-07 · 총 3콜.

| 항목 | 실측 결과 |
|---|---|
| 최대 회사 수 | **100건.** 101개를 넣으면 `status 021` 로 거절된다 |
| 혼합 내성 | 없는 `corp_code` 가 섞여도 **묶음이 죽지 않는다.** 나머지는 정상 응답 |
| `fs_div` | **CFS·OFS 가 한 응답에 섞여 온다.** 요청 파라미터가 아니다 |
| 회사당 행 | 연결·별도 둘 다 있으면 30행, 하나만 있으면 15행 |
| 단건 대조 | `fnlttSinglAcnt` 와 공통 13개 값 **전부 일치** |
| 무응답 | 100개사 요청에 90개사 응답 — 그 해 보고서가 없는 것 |

**`fs_div` 가 파라미터가 아닌 것이 이 티켓의 이득이다.** `SinglAcntAll` 처럼 연결·별도를 따로
부르지 않아도 되므로 호출이 절반이다.

### 함정 다섯 — 전부 실측으로 잡았다

**① `당기순이익(손실)` 이 회사마다 정확히 2행 온다.**

```
CFS IS 당기순이익(손실)  309,374,667   ord 29
CFS IS 당기순이익(손실)  309,374,667   ord 30      ← 같은 값, ord 만 다름
```

접지 않으면 **집계가 2배**가 된다. 전 종목 21,323행에서 **값이 갈린 것은 0건**이었지만,
표본에 없다는 것이 없다는 뜻은 아니므로 **값이 다르면 접지 않고 경고로 남기도록** 했다.

**② 통화가 원화만이 아니다.**

```
KRW 291,287   USD 1,241   CNY 643   JPY 135   HKD 26      (외화 2,045행)
```

원화로 환산하지 않고 `currency` 를 그대로 남겼다. **모르고 합치면 값이 완전히 틀린다.**

**③ 결산월이 12월이 아닌 회사가 55곳 있다.**

`bsns_year` 는 2023인데 기준일이 `2023.06.30 현재` 인 회사들이다. 사업연도와 달력연도가
같다고 가정하면 어긋난다.

**④ 같은 뜻인데 계정 이름이 둘이다.** `영업이익` 과 `영업이익(손실)` 이 모두 나온다
(후자가 71개사). 이름만 보고 `영업이익` 으로 거르면 **71개사가 통째로 빠진다.**

계정명은 전부 **32종**이고, 그중 **18종은 표준 14종 밖**이다 — 대부분 금융·보험업
전용이다(`순이자손익` · `보험계약부채` · `예수부채` 등). 다만 행 수로는 4,978행(**1.70%**)
이라, 표준 14종만 써도 대부분이 덮인다.

**⑤ 원본 디렉터리는 수집 실행 단위가 아니다.** 정규화를 `glob` 으로 짰더니 실측이 남긴
파일이 섞여 2,388행이 더 얹혔다. **manifest 가 가리키는 파일만 읽도록** 고쳤다.

## 5. 제안 DDL

착지 테이블은 `staging` 스키마에 만든다 — `V9` 가 그 합의(S15P21A504-120 회신 5장)를 따라
`staging.dart_otr_cpr_invstmnt` 를 그렇게 두었고, 조회 API 는 이 스키마를 읽지 않는다.

**응답을 행 단위 그대로 보관한다.** 넓은 표로 펴는 것은 해석이므로 소비처가 정한다.

```sql
-- ────────────────────────────────────────────────
-- DART 다중회사 주요계정 (전 종목 재무 수치)
-- ────────────────────────────────────────────────
CREATE TABLE staging.dart_fnltt_acnt (
    id                 BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    -- 스키마를 넘는 참조라 public 을 명시한다 (V9 와 같은 이유).
    corp_code          VARCHAR(8)   NOT NULL REFERENCES public.company (corp_code),
    bsns_year          SMALLINT     NOT NULL,
    reprt_code         VARCHAR(5)   NOT NULL,
    ord                SMALLINT     NOT NULL,

    stock_code         VARCHAR(6),
    rcept_no           VARCHAR(14),

    fs_div             VARCHAR(3)   NOT NULL,      -- CFS 연결 / OFS 별도
    fs_nm              VARCHAR(20),
    sj_div             VARCHAR(10)  NOT NULL,      -- BS 재무상태표 / IS 손익계산서
    sj_nm              VARCHAR(50),
    account_nm         VARCHAR(100) NOT NULL,
    currency           VARCHAR(5),

    thstrm_dt          VARCHAR(30),
    thstrm_amount      NUMERIC(24, 0),
    frmtrm_amount      NUMERIC(24, 0),
    bfefrmtrm_amount   NUMERIC(24, 0),

    collected_at       TIMESTAMPTZ  NOT NULL DEFAULT now(),

    CONSTRAINT dart_fnltt_acnt_uk
        UNIQUE (corp_code, bsns_year, reprt_code, ord),
    CONSTRAINT dart_fnltt_acnt_year_check
        CHECK (bsns_year BETWEEN 1900 AND 2100),
    CONSTRAINT dart_fnltt_acnt_fs_div_check
        CHECK (fs_div IN ('CFS', 'OFS')),
    CONSTRAINT dart_fnltt_acnt_rcept_no_check
        CHECK (rcept_no IS NULL OR rcept_no ~ '^[0-9]{14}$')
);
```

컬럼 주석은 다음과 같이 붙인다. `V9` 처럼 **함정을 아는 사람만 아는 채로 두지 않는다.**

| 컬럼 | 주석에 담을 내용 |
|---|---|
| 테이블 | 응답을 행 단위 그대로 보관. 적재는 `(corp_code, bsns_year, reprt_code)` 단위로 지우고 다시 넣는다 — **원천이 업무키 유일성을 보장하지 않는다(당기순이익이 2행 온다)** |
| `ord` | 응답 안 행 번호. UNIQUE 키 구성요소. 전 종목 293,332행에서 `(corp_code, bsns_year, ord)` 중복 0. **`account_nm` 을 키에 쓰면 당기순이익 2행이 충돌한다** |
| `account_nm` | 32종이며 18종은 표준 14종 밖(금융·보험업 전용, 4,978행 · 1.70%). **같은 뜻으로 `영업이익` 과 `영업이익(손실)` 이 모두 나오므로(후자 71개사) 이름으로 거를 때 둘 다 봐야 한다** |
| `currency` | KRW 가 아닌 행이 2,045건(USD·CNY·JPY·HKD). **원화 환산하지 않았다 — 통화를 무시하고 합치면 값이 틀린다** |
| `thstrm_dt` | 당기 기준일 원문. BS 는 `2023.12.31 현재`, IS 는 `2023.01.01 ~ 2023.12.31`. **결산월이 12월이 아닌 회사가 55곳** 있어 원문을 보존한다 |
| `frmtrm_amount` | Y년 응답의 이 값은 Y-1년 응답의 `thstrm_amount` 와 같아야 하며 224,323쌍 중 94.658% 일치. **나머지는 소급 재작성** — 6장 판단 ③ |
| `fs_div` | CFS=연결, OFS=별도. 한 응답에 둘 다 온다. **폴백 여부는 소비처가 정한다 — 착지에서 접지 않는다** |

조회용 인덱스 하나를 둔다. 삭제 경로는 UNIQUE 키가 커버한다.

```sql
CREATE INDEX dart_fnltt_acnt_lookup_idx
    ON staging.dart_fnltt_acnt (corp_code, bsns_year, fs_div);
```

### 폭을 정한 근거 (전 종목 293,332행 실측)

| 컬럼 | 실측 최대 | 제안 | 여유를 둔 이유 |
|---|---|---|---|
| `account_nm` | 17자 · 32종 | `VARCHAR(100)` | 금융업 계정이 길다. 업종이 늘면 더 길어질 수 있다 |
| `thstrm_dt` | 23자 | `VARCHAR(30)` | 기간 표기가 가장 길다 |

| `currency` | 3자 · 5종 | `VARCHAR(5)` | ISO 4217 은 3자다 |
| `fs_div`·`sj_div` | 3자 · 2자 | 그대로 | 값이 2종씩뿐이라 `CHECK` 를 걸었다 |

## 6. 판단이 필요한 곳 — 넷

### ① UNIQUE 키를 `ord` 로 잡는 것에 동의하는가

`V9` 의 `row_no` 와 같은 논리다. **업무키를 쓸 수 없다는 것이 실측으로 확인됐다.**

```
(corp_code, bsns_year, fs_div, sj_div, account_nm)
    원본에서 당기순이익이 회사마다 2행 → 이 키로는 충돌한다
    정규화가 접은 뒤에는 중복 0 — 그러나 원천이 보장한 것이 아니다

(corp_code, bsns_year, reprt_code, ord)
    전 종목 293,332행에서 중복 0
    원본 순서가 보존된다
    기업-연도 단위로 지우고 다시 넣으므로 재수집 때 번호가 바뀌어도 무방하다
```

### ② 착지에 원본을 넣을까, 접은 것을 넣을까 — **가장 중요하다**

당기순이익 2행을 어떻게 할지다.

| 안 | 내용 | 장 | 단 |
|---|---|---|---|
| **A** | **원본 그대로** 314,655행 | 착지 원칙에 맞다. 원본과 1:1 로 대조된다 | 소비처가 매번 접어야 하고, 잊으면 2배가 된다 |
| **B** | 접은 것 293,332행 | 쓰기 쉽다 | 착지 테이블인데 이미 가공이 들어간다 |

**권고: A.** 착지는 "도서관이 준 그대로"가 원칙이고, 접는 규칙(값이 같을 때만 접는다)은
바뀔 수 있는 판단이다. 착지에 굳혀 두면 나중에 되돌릴 수 없다. 대신 **집계할 때 반드시
중복을 접으라는 경고를 테이블 주석에 박았다** — `V9` 의 `is_total` 과 같은 방식이다.

A 로 가면 위 DDL 그대로이고, B 로 가면 행 수만 293,332로 줄어든다.

### ③ 소급 재작성 — 어느 값이 정본인가 (기획과)

```
2022년 보고서가 말한 2022년 매출        =  그 해에 발표한 값
2023년 보고서가 말한 "작년(2022) 매출"  =  나중에 고쳐 적은 값
```

**224,323쌍 중 11,984쌍(5.3%)이 다르고, 1,026개사(39%)에서 계정을 가리지 않고 나온다.**
상위 회사는 100행 넘게 전부 어긋난다 — 회계기준·연결범위가 바뀌면 통째로 다시 쓰기 때문이다.

| 안 | 내용 | 언제 맞나 |
|---|---|---|
| **A** | 각 해 보고서의 **당기값** | "2022년에 이 회사는 얼마를 벌었다고 발표했나" |
| **B** | 최신 보고서의 **전기값** | "지금 기준으로 2022년을 다시 보면 얼마인가" — 시계열 비교에 유리 |

**지금은 A 로 담았다** (각 해가 스스로 말한 값). 착지 테이블에는 **셋 다 들어 있으므로**
(`thstrm`·`frmtrm`·`bfefrmtrm`) 나중에 B 로 바꿔도 **재수집이 필요 없다.**
서비스 화면이 어느 쪽을 보여줄지만 정해주면 된다.

### ④ `collection_run` 의 `run_type` 을 새로 만들까

`V1` 의 CHECK 에 `FINANCIAL` 이 이미 있고 `V9` 가 `INVESTMENT` 를 더했다.

```
그대로 씀   run_type = 'FINANCIAL'        ALTER 불필요. 10개사 수집과 이력이 섞인다
새로 만듦   run_type = 'FINANCIAL_ALL'    ALTER 필요. 재실행 대상 판단이 분리된다
```

**권고: `FINANCIAL` 재사용.** 백엔드 소유 제약을 건드리지 않는 쪽이 낫고, 두 실행은
`target_year` 와 `message` 로 구분된다. 분리가 필요하다고 보시면 `ALTER` 를 함께 넣겠다.

## 7. 적재 방식

`V9` 의 `load_investment.py` 와 같은 모양으로 짜겠다. 승인 뒤에 만든다.

```
키        UNIQUE (corp_code, bsns_year, reprt_code, ord)
방식      업무키 upsert 가 아니라 (corp_code, bsns_year) 단위로 지우고 다시 넣는다
안전장치  ① 삭제와 삽입을 트랜잭션 하나로 — 실패하면 통째로 되돌아간다
          ② 적재 전후 행 수 가드 — 예상과 다르면 롤백 + 종료코드 1
```

②를 넣는 이유는 84 의 유실 전례다. **값이 틀린 것보다 조용히 사라지는 것이 무섭다.**

**②가 실제 차단 요소다.** `V9` 착지 테이블도 같은 이유로 아직 적재를 못 하고 있다.
