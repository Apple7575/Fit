# 사업보고서 파이프라인 — 전 상장사 확대 구상

100개사로 검증한 파이프라인을 남은 2,499개사로 넓힐 때의 설계다.

- 작성: 데이터 담당 (tpdms3048)
- 날짜: 2026-09-09
- 관련: S15P21A504-73 (MR !85), 팀장 요청
- **전제 — Hadoop 도입은 확정이다.** Kafka 는 검토 중이다. 그래서 이 문서는
  "쓸지 말지" 가 아니라 **"어디에 두면 실제로 이득이 나는지"** 를 정한다.
- 이 문서의 모든 시간·용량은 **100개사 실행에서 실측한 값**의 외삽이다. 추정이
  아니라 잰 값이며 어디서 쟀는지 함께 적는다.

## 2. 병목이 어디인가 — 실측

| 단계 | 실측 | 11,395건 환산 |
|---|---|---|
| 수집 (DART document.xml) | 340건/분 | **34분** |
| 파싱 (XML → 표·문단) | 4.25초/건, 단일 프로세스 | **13.5시간** |
| LLM (문서당 2회 호출) | 9.0초/건, 순차 | **28.6시간** |
| 시드 생성 + 검증 | 전체 몇 분 | 몇 분 |

**지배적 병목은 LLM 추론이다.** 수집은 34분이라 논외다. 파싱은 문서 단위로 완전히
독립이라 워커 수만큼 그대로 나뉜다 — 여기가 Hadoop 이 들어갈 자리다.

### LLM 동시 요청을 실측했다

| 방식 | 실측 | 11,395건 환산 |
|---|---|---|
| 순차 | 8.6건/분 | 28.6시간 |
| 동시 2 | 17.5건/분 (2.0배) | 14.3시간 |
| **동시 4** | **33.6건/분 (3.9배)** | **7.3시간** |
| 동시 8 | 29.1건/분 (3.4배) | 8.4시간 — **동시 4보다 느리다** |

동시 4 까지 거의 선형이고 8에서 꺾인다. KV 캐시 1.9GB 포화 지점이며 운영 안내 4절의
"12K 짜리는 1개, 2K 짜리는 5~6개" 와 맞는다.

**이 숫자가 설계를 정한다.** 파싱을 아무리 분산해도 LLM 이 7.3시간이면 전체는
7.3시간 아래로 못 내려간다. 클러스터 노드를 늘려서 줄어드는 것은 파싱 13.5시간뿐이다.

## 3. Hadoop 을 어디에 두는가

### 두는 자리 — 파싱

파싱은 **문서 하나가 곧 하나의 독립 작업**이다. 문서 사이에 공유 상태가 없고 셔플이
없다. 분산 처리의 교과서적 형태이고, 여기 두면 실제로 시간이 준다.

| 워커 | 파싱 시간 |
|---|---|
| 1 | 13.5시간 |
| 4 | 3.4시간 |
| 8 | 1.7시간 |
| 16 | 0.8시간 |

### 구성

```
HDFS   /raw/opendart/filings/annual_report/{bsns_year}/{rcept_no}.xml     69GB
       /staged/business_report/{segment,facility,product,rnd}/*.parquet
       /staged/business_report/passages/*.parquet

Spark on YARN   파싱 잡. sc.binaryFiles 로 XML 을 (경로, 바이트)로 읽고
                mapPartitions 안에서 지금 파서를 그대로 부른다
```

**지금 코드를 다시 쓰지 않는다.** `pipeline/business_report/` 는 파일 경로가 아니라
`Document(path)` 하나만 받고, 그 안에서 네 파서가 도는 구조다. Spark 쪽은
`binaryFiles` 로 받은 바이트를 임시 파일이나 `BytesIO` 로 넘기면 되고,
`parse_business_reports.py` 의 문서 1건 처리 부분만 함수로 떼면 된다.

### HDFS 를 쓸 때 주의할 것

- **작은 파일 문제는 여기서 심각하지 않다.** 파일 11,395개 × 평균 6MB 다. 블록
  128MB 기준으로 파일당 1블록을 못 채우지만, NameNode 메모리는 파일당 약 150바이트라
  11,395개면 무시할 수준이다. 수백만 개였다면 SequenceFile 로 묶어야 한다
- **`binaryFiles` 는 파일당 1파티션**을 만든다. 이 경우엔 오히려 유리하다 —
  문서 단위 병렬이 그대로 파티션 단위가 된다
- **파이썬 의존성**(lxml · PyYAML)을 워커에 배포해야 한다. venv 를 zip 으로 묶어
  `--archives` 로 넘기는 방식이 가장 단순하다
- **산출은 Parquet 로 쓴다.** 지금은 CSV 인데, 분산으로 쓰면 워커마다 파일이 생겨
  한 CSV 에 동시 쓰기를 할 수 없다. Parquet 는 파티션 파일이 자연스럽고 마지막에
  시드용 CSV 로 한 번만 모으면 된다

### 원문 수집은 분산하지 않는다

DART API 는 **일일 20,000회 한도**가 있고 호출 간격 제한도 있다. 워커를 늘리면
한도를 더 빨리 소진할 뿐 34분이 줄지 않는다. 수집은 단일 노드에서 돌리고 HDFS 에
올리는 것으로 끝낸다.

## 4. Kafka 를 어디에 두는가 (검토 중)

### 두면 이득이 나는 자리 — LLM 작업 큐

파싱(빠름·분산)과 LLM(느림·단일 GPU) 사이의 속도 차가 12배다. 그 사이에 큐를 두는
것은 억지가 아니라 이 구조가 원래 요구하는 것이다.

```
Spark 파싱 ──produce──► Kafka  br.passages  (파티션 4)
                                    │
                          consumer group: llm-workers
                                    ▼
                        GPU 워커 (vLLM, 동시 4) ──► br.text ──► 시드 생성
```

**파티션 4 = GPU 동시 처리 4** 로 맞춘다. 실측에서 동시 4가 최적이므로 컨슈머를 더
붙여도 GPU 가 못 받는다. 파티션 수를 처리 능력에 맞추면 그 사실이 구조에 드러난다.

### 얻는 것

- **백프레셔.** 파싱이 아무리 빨라도 GPU 가 소화하는 만큼만 흘러간다. 지금은
  passages.jsonl 을 통째로 만들어 두고 순차로 읽는다
- **재시도·재개가 오프셋으로 정리된다.** 지금은 결과 CSV 를 다시 읽어 차집합을 내는
  방식이라, 중단 시점의 마지막 문서가 반쯤 처리됐는지 알 수 없다 (실제로 겪어서
  손으로 마지막 행을 지웠다)
- **중복이 이미 막혀 있다.** 컨슈머가 at-least-once 여도 `company_text` 의
  UNIQUE (corp_code, fiscal_year, attr_key, seq) 가 중복을 거른다. **at-least-once
  + DB UNIQUE = 사실상 한 번**이라 Kafka 의 가장 성가신 부분이 여기서는 문제가 아니다
- **뉴스와 인프라를 공유한다.** 뉴스는 진짜 스트림이라 Kafka 가 원래 맞는 자리다.
  사업보고서가 그 위에 얹히는 그림이 자연스럽다

### 안 두면 잃는 것 — 솔직히 적으면

지금의 파일 기반 이어받기로도 11,395건은 처리된다. Kafka 없이 못 하는 일은 없다.
차이는 **운영 편의**다. 11,395건을 하룻밤 돌리는데 GPU 가 중간에 죽었을 때, 오프셋이
있으면 그냥 컨슈머를 다시 띄우면 되고 없으면 CSV 를 다시 읽어 차집합을 낸다.

그래서 판단 기준은 이렇게 두는 것이 맞다.

- **한 번만 돌릴 것이면** 파일 기반으로 충분하다
- **분기·연간으로 반복하고 뉴스도 Kafka 로 갈 것이면** 지금 넣는 것이 싸다

## 5. GPU 노트북을 어떻게 쓰는가

팀별로 받은 노트북이 있다. 두 갈래이고 **어느 쪽인지에 따라 설계가 달라진다.**

### (가) 노트북이 추론을 직접 돌리는 경우

공유 카드(jupyter05 GPU 1의 절반, 22GB) 대신 팀 전용 자원을 쓸 수 있다. 다른 팀
눈치를 안 봐도 되고 KV 캐시를 더 잡아 동시 수를 올릴 수 있다.

**다만 모델이 안 들어갈 수 있다.** 지금 쓰는 Qwen3-32B-AWQ 는 가중치만 19GB 다.

| 노트북 VRAM | 가능한 것 |
|---|---|
| 24GB (RTX 4090 Laptop 은 16GB, 데스크톱급 외장이면 24GB) | Qwen3-32B-AWQ 가 빠듯하게 들어간다 |
| 16GB | Qwen3-14B-AWQ 정도. 품질 재검증 필요 |
| 8~12GB | Qwen3-8B 급. 추출 품질 표본 확인이 반드시 선행돼야 한다 |

모델을 바꾸면 **프롬프트를 다시 맞춰야 한다.** 이번에 rd_field 하나를 맞추는 데
프롬프트를 세 번 고쳤고, 마지막에는 모델이 프롬프트 예시를 그대로 베끼는 것을
원문 대조로 막았다. 작은 모델일수록 이런 일이 늘어난다.

### (나) 노트북이 클러스터 노드·운영 단말인 경우

추론은 jupyter05 에 두고 노트북은 Hadoop 워커나 Kafka 브로커로 쓴다. 파싱
13.5시간을 나누는 데 바로 보탬이 된다.

### 어느 쪽이든 공통

**GPU 워커는 클러스터 밖에 둔다.** YARN 이 GPU 스케줄링까지 하게 만들지 않는다.
vLLM 은 상주 서버로 띄워 두는 것이 맞고, Spark 태스크마다 모델을 올렸다 내리면
로딩만 1~2분씩 든다. 그래서 4장 그림처럼 **Kafka(또는 파일 큐)를 경계로 배치 클러스터와
추론 서버를 끊어 두는 구조**가 자연스럽다.

## 7. 지금 코드에서 바꿔야 할 것

| 단계 | 무엇 | 왜 |
|---|---|---|
| ② | 문서 1건 처리를 순수 함수로 분리 | Spark `mapPartitions` 안에서 부르려면 파일 I/O 와 분리돼야 한다 |
| ② | 산출을 CSV → Parquet | 워커마다 파일이 생긴다. 한 CSV 에 동시 쓰기는 안 된다 |
| ② | venv 를 zip 으로 묶어 `--archives` | 워커에 lxml·PyYAML 이 있어야 한다 |
| ④ | `ThreadPoolExecutor(4)` | 실측 3.9배. 8은 오히려 느리다 |
| ④ | 실패 건 별도 기록 | 11,395건이면 개별 실패를 눈으로 못 쫓는다 |
| ⑤ | 시드 생성이 Parquet 를 읽게 | 지금은 `staged/business_report/*.csv` 를 읽는다 |
| 전체 | 실행 이력 테이블 | F-29(S15P21A504-36)가 원래 이 자리다 |

**검증 7축은 그대로 쓴다.** CSV 만 읽으므로 규모와 무관하다. 다만 D축이 실패 목록을
전부 출력하므로 건수가 커지면 요약 + 상위 N건으로 바꿔야 한다.

## 8. 단계적 실행 제안

한 번에 2,499개사를 돌리지 않는다. 파서는 **매출 상위 100개사에서만 검증됐고**
업종이 넓어지면 새 표 모양이 나온다 — 금융·건설·지주는 사업보고서 구조가 다르다.

| 차수 | 대상 | 목적 | 예상 |
|---|---|---|---|
| 0차 | 지금 100개사 | Spark·Kafka 배선을 같은 입력으로 재현 (결과가 같아야 한다) | 30분 |
| 1차 | +200개사 (누적 300) | 업종 확대 시 파싱 성공률 확인 | 2시간 |
| 2차 | +700개사 (누적 1,000) | 1차에서 늘린 패턴 검증 | 4시간 |
| 3차 | 나머지 전부 | | 5시간 |

**0차를 먼저 두는 이유**는 인프라를 바꾸면서 결과까지 같이 바뀌면 원인을 못 가리기
때문이다. 지금 100개사 결과가 시드로 커밋돼 있으므로 Spark 로 돌린 결과가 그것과
바이트 단위로 같은지 대조할 수 있다.

각 차수 뒤에 `parse_summary.csv` 판정 분포를 보고 `patterns.yaml` 을 늘린다.
**코드가 아니라 YAML 을 늘리는 것이 원칙이다** (F-27 AC1).

## 9. 정해야 할 것

1. **Hadoop 클러스터가 어디서 도는가** — SSAFY 제공 클러스터인지, 팀 노트북으로
   구성하는지, 단일 노드 pseudo-distributed 인지. 워커 수가 파싱 시간을 정한다
2. **GPU 노트북의 VRAM** — 24GB 미만이면 Qwen3-32B-AWQ 가 안 올라가고 모델을
   바꿔야 한다. 모델이 바뀌면 프롬프트 재검증이 따라온다 (5장)
3. **Kafka 도입 여부** — 한 번만 돌릴 것이면 파일 큐로 충분하다. 반복 실행과 뉴스
   파이프라인까지 보면 지금 넣는 것이 싸다 (4장)
4. **LLM 대상 범위** — 2,499개사 전부인가 상위 N개사인가. `main_product` 는 파싱이라
   전부 가능하고 나머지 5종만 범위 판단이 필요하다
5. **실행 주기** — 사업보고서는 3월에 몰린다. 연 1회 배치인지 정정 공시까지 따라갈지

## 10. 하지 말아야 할 것

- **수집을 분산하기.** DART 일일 20,000회 한도다. 워커를 늘리면 한도만 빨리 쓴다
- **원문을 Git 에 넣기.** 69GB 다. HDFS 에 두고 계보만 `manifests/` 로 남긴다
  (저장 기준 7장)
- **GPU 를 YARN 스케줄링에 넣기.** 태스크마다 모델을 올렸다 내리면 로딩만 1~2분이다.
  vLLM 은 상주 서버로 두고 큐로 연결한다
- **파서 성공률이 떨어졌다고 임계값을 푸는 것.** D축 허용오차 5%는 값이 맞는지
  가리는 유일한 장치다. 커버리지가 아쉬우면 패턴을 늘리지 검증을 느슨하게 하지
  않는다 (팀장 기준 4항)
- **인프라 교체와 파서 수정을 같은 차수에 하기.** 0차에서 결과가 달라지면 Spark
  때문인지 파서 때문인지 못 가린다
