## 2. 무엇이 어디서 도는가

| 장비 | 올리는 것 | 하는 일 | 안 하는 일 |
|---|---|---|---|
| **EC2 A** | NameNode · ResourceManager · DataNode · NodeManager · **Kafka** | 클러스터 관리, 파싱 절반, 작업 큐 | GPU 없음 |
| **EC2 B** | DataNode · NodeManager | 파싱 절반 | |
| **jupyter05** | vLLM (Qwen3-32B-AWQ) | **문장 해석만** | 하둡 워커 아님 |
| **개발 PC** | 수집기 · 오케스트레이션 · LLM 컨슈머(잠정) | DART 에서 원문 받기, 순서 지휘 | |

**GPU 를 YARN 에 넣지 않는 이유** — Spark 태스크마다 32B 모델을 GPU 에 올렸다 내리면
로딩만 1~2분씩 든다. 모델은 상주 서버로 한 번 띄워 두고 HTTP 로 부르는 것이 맞다.
그래서 배치 클러스터와 추론 서버를 **큐로 끊어 둔다.**

## 3. 데이터가 흐르는 길

| | 단계 | 어디서 | 입력 → 출력 |
|---|---|---|---|
| ① | **수집** | 개발 PC | DART API → 원문 XML 11,395건 (69GB) → HDFS |
| ② | **파싱** | Spark on YARN | XML → 표·문단 추출 → Parquet 5종 |
| ③ | **적재(큐)** | Kafka | 문장 해석이 필요한 구간의 **주소**를 토픽에 넣음 |
| ④ | **소비** | LLM 컨슈머 | 토픽에서 하나씩 꺼냄 (동시 4) |
| ⑤ | **추론** | jupyter05 vLLM | 문단 → 사업 설명·키워드·연구 분야 |
| ⑥ | **정리** | 개발 PC | Parquet + 추론 결과 → 시드 CSV → 검증 7축 → PostgreSQL |

### ②에서 나오는 것

| Parquet | 내용 | 다음 단계 |
|---|---|---|
| `segment_revenue` | 부문별 매출 | 바로 ⑥ |
| `facility` | 시설투자 | 바로 ⑥ |
| `main_product` | 주요 제품 | 바로 ⑥ |
| `rd_expense` | 연구개발비 | 바로 ⑥ |
| `passages` | LLM 에 넘길 원문 구간 | **③ 큐로** |

네 개는 표에서 규칙으로 뽑아 GPU 가 필요 없다. `passages` 만 큐를 탄다.

## 4. Hadoop 구성

### 왜 쓰는가

파싱이 **문서 하나 = 독립 작업 하나**다. 문서끼리 주고받을 것이 없어 나누면 그대로
빨라진다. 그리고 69GB 를 두 노드가 같이 읽어야 해서 **공유 저장소가 실제로 필요하다** —
없으면 파일을 손으로 갈라 각 노드에 복사해야 한다.

### 디렉터리

```
/raw/opendart/filings/annual_report/{연도}/{접수번호}.xml     69GB · 불변
/staged/business_report/jobs.parquet                        작업 목록
/staged/business_report/{segment_revenue,facility,...}/      파싱 산출
```

연도로 나누는 이유는 한 디렉터리에 11,395개가 몰리지 않게 하기 위해서다.

### 용량

| | |
|---|---|
| 원문 | 69GB |
| replication 2 | **138GB** |
| 파싱 산출(Parquet) | 3GB 미만 |
| 물리 여유 (307GB × 2) | 614GB |

**충분하다.** replication 은 DataNode 가 2개이므로 2로 둔다.

### 설정 시작값

노드당 15GiB 에서 OS 1GB · DataNode 1GB · NodeManager 1GB 를 뺀다.
A 는 NameNode · ResourceManager · Kafka 로 3GB 를 더 뺀다.

| | EC2 A | EC2 B |
|---|---|---|
| `yarn.nodemanager.resource.memory-mb` | 8192 | 11264 |
| `yarn.nodemanager.resource.cpu-vcores` | 3 | 4 |
| `dfs.replication` | 2 | 2 |

```
spark.executor.instances      3
spark.executor.cores          2
spark.executor.memory         2g
spark.executor.memoryOverhead 2g      ← 기본값으로 두면 안 된다
```

> **`memoryOverhead` 를 줄이지 마세요.** 파싱이 문서 하나에 약 450MB 를 쓰는데(실측),
> PySpark 는 파이썬 프로세스가 JVM **밖에서** 돌아 `executor.memory` 가 아니라 이
> 값을 먹습니다. 기본값(10% = 200MB)이면 컨테이너가 OOM 으로 죽습니다.

### 파이썬 환경

노드가 2대뿐이라 **각 노드에 직접 설치**하는 편이 단순하다.

```bash
python3 -m venv ~/brenv && ~/brenv/bin/pip install -r requirements.txt
~/brenv/bin/python -c "import lxml.etree as e; print(e.LXML_VERSION, e.LIBXML_VERSION)"
#   두 노드가 (6, 1, 2, 0) (2, 11, 9) 로 같아야 한다
```

> **버전이 다르면 결과가 달라집니다.** 원문에 마크업이 깨진 문서가 섞여 있어 복구
> 모드로 읽는데, **복구 방식이 lxml/libxml2 버전마다 미묘하게 다릅니다.** 표가 하나
> 더 잡히거나 덜 잡히면 금액이 조용히 바뀝니다. `requirements.txt` 가 `lxml==6.1.2`
> 로 고정해 두었습니다.

### 원문 수집은 분산하지 않는다

DART API 가 **일일 20,000회 한도**다. 워커를 늘려도 34분이 줄지 않고 한도만 빨리
쓴다. 개발 PC 에서 받아 HDFS 로 올린다. 이미 받아 둔 487건(2.95GB)은 다시 받지 않는다.

## 5. Kafka 구성

### 왜 쓰는가

파싱은 빠르고 LLM 은 느리다 — **10배 이상 차이**다. 그 사이에 큐가 없으면 빠른 쪽이
느린 쪽을 기다리며 서 있거나, 만들어 둔 작업을 파일로 쌓아 두고 순서를 사람이
관리해야 한다.

| 얻는 것 | 설명 |
|---|---|
| **백프레셔** | GPU 가 소화하는 만큼만 흘러간다 |
| **재개** | GPU 가 죽어도 오프셋부터 다시. 지금은 결과 파일을 다시 읽어 차집합을 낸다 |
| **재시도** | 실패 건만 다시 넣는다 |
| **뉴스와 공유** | 뉴스는 진짜 실시간 스트림이라 Kafka 가 원래 맞는 자리다 |

### 구성

```
브로커      EC2 A · KRaft 모드 (ZooKeeper 없음) · 힙 1GB
토픽        br.passages   파티션 4 · replication 1
            br.text       파티션 4 · replication 1   (결과. 없어도 되지만 계보가 남는다)
컨슈머 그룹  llm-workers
```

- **파티션 4 = GPU 동시 처리 4.** 컨슈머를 더 붙여도 GPU 가 못 받는다. 파티션 수를
  처리 능력에 맞추면 그 사실이 구조에 드러난다
- **replication 1** — 브로커가 하나라 다른 값을 줄 수 없다. 배치 작업이고 원본이
  HDFS 에 남아 있어 토픽을 잃어도 다시 만들면 된다
- **메시지 11,395건 · 메타데이터뿐**이라 브로커 하나로 충분하다

### 메시지에 원문을 넣지 않는다

```json
{"corp_code":"00126380","fiscal_year":2024,"rcept_no":"20250311001085",
 "passages_path":"hdfs:///staged/business_report/passages/part-00003.parquet",
 "row_id":142}
```

구간 텍스트가 문서당 12,000자다. 메시지에 담으면 토픽이 수백 MB 가 되고 브로커 힙
1GB 로는 부담이다. **주소만 보내고 컨슈머가 HDFS 에서 읽는다.**

### 중복은 이미 막혀 있다

컨슈머가 같은 작업을 두 번 처리해도(at-least-once) DB 의
`UNIQUE (corp_code, fiscal_year, attr_key, seq)` 가 거른다. **Kafka 에서 제일 성가신
부분이 여기서는 문제가 아니다.**

### 파일 기반 재개도 남긴다

Kafka 없이 개발 PC 단독으로도 같은 코드가 돌아야 한다. 파서를 고칠 때마다 클러스터를
띄우지 않기 위해서다. **입력·출력 위치만 설정으로 가른다.**

## 6. 규모와 시간 — 실측 기준

| 단계 | 실측 | 11,395건 환산 |
|---|---|---|
| 수집 | 340건/분 | **34분** |
| 파싱 (슬롯 6) | 4.25초/건 | **2.2시간** |
| LLM (동시 4) | 아래 참고 | **11~12시간** |
| 시드·검증·적재 | | 몇 분 |

### LLM 시간은 11~12시간으로 확정한다

같은 측정을 이틀에 걸쳐 했더니 값이 달랐다 (동시 4 기준 3.9배 ↔ 2.5배).

**원인은 메모리가 아니라 연산 경합이다** (팀장 회신). GPU 1의 메모리는 절반씩
나뉘어 있지만 **연산 코어는 같은 카드를 두 팀이 나눠 쓴다.** 다른 팀이 돌리는 동안엔
느려지고 시간대를 골라도 통제할 수 없다. 그래서 **느린 쪽(11~12시간)으로 잡는다.**

배치 시간대 제한은 없다. 8~12시간 연속 점유가 가능하다.

### 동시 요청을 올려도 이득이 없다 — 반복 측정으로 확인

본문 6,000자 그대로, 3회씩 재서 중앙값을 봤다.

| 동시 | 측정값 (호출/분) | 중앙값 |
|---|---|---|
| 4 | 18.2 · 29.0 · 28.0 | 28.0 |
| 6 | 26.2 · 22.7 · 21.0 | 22.7 |
| 8 | 21.8 · 22.0 · 23.3 | 22.0 |
| 10 | 25.0 · 23.9 · 22.9 | 23.9 |

**같은 설정 안의 편차가 설정 간 차이보다 크다.** 동시성을 올려도 얻는 것이 없다.

이유가 서버 로그에 있다 — **KV 캐시 총량이 15,840 토큰**이다. 우리 요청이 입력
2,766 + 출력 123 ≈ 2,900 토큰이라 **동시 5개 남짓**만 들어가고 나머지는 대기한다.
계산도 맞는다: Qwen3-32B(64층 · KV 8헤드 · head_dim 128)에 fp8 이면 토큰당 128KB 이고
1.9GB ÷ 128KB ≈ 15,500 토큰이다.

**그래서 Kafka 파티션은 4로 둔다.** 더 늘려도 GPU 가 못 받는다.

### 현재 vLLM 설정 (팀장 회신)

| 인자 | 값 |
|---|---|
| 모델 | Qwen/Qwen3-32B-AWQ (4비트), float16 |
| `--gpu-memory-utilization` | 0.47 (예산 21.6GB · 실점유 22.7GB) |
| `--max-model-len` | 12288 |
| `--kv-cache-dtype` | fp8 |
| `--enforce-eager` | **켜짐** — CUDA 그래프 끔. 1GB 아끼고 속도 20~30% 손해 |
| `--enable-prefix-caching` | 켜짐 |
| `--max-num-seqs` | 미설정 (기본값). **병목이 아니다** |

`--enforce-eager` 를 끄면 20~30% 빨라지지만 메모리가 1GB 늘어 실점유가 23.7GB 가
된다. 재시작 후 확인 기준인 23,000MiB 를 넘으므로 **32B 를 쓰는 한 못 끈다.**

**재시작은 우리가 해도 된다.** 이 인스턴스는 우리 팀 전용이다. 세 가지를 지킨다.

    gpu-memory-utilization 0.47 을 넘기지 않는다
    CUDA_VISIBLE_DEVICES=1 밖으로 나가지 않는다
    재시작 후 nvidia-smi 에서 GPU 1 이 23,000MiB 아래인지 확인한다

스크립트는 `~/vllm/vllm-setup.sh` (stop · start · test · logs). 모델은 파일 상단의
`MODEL=` 만 고친다.

### GPU 추가는 불가하다

`nvidia-smi` 캡처의 0MiB 는 그 순간 비어 있었던 것이고 우리 몫이 아니다. 지금은
GPU 0·2 도 다른 팀이 쓴다. **할당은 GPU 1 절반으로 고정이다.**

### 전체

파싱과 LLM 을 겹쳐 돌리면 **약 12시간**, 순차면 **약 14시간**. 하룻밤 배치다.

**LLM 이 바닥이다.** EC2 를 더 붙여도, GPU 할당을 늘려도(불가), 동시성을 올려도
(이득 없음) 줄지 않는다. 남은 길은 **요청을 가볍게 하거나 모델을 낮추는 것** 둘뿐이고
아래 표에 실측을 적었다.

### 시간을 줄이는 두 길 — 실측

| | 처리량 (호출/분, 동시 12) | 11,395건 | 품질 |
|---|---|---|---|
| 지금 (6,000자 · 32B) | 26 | 11~12시간 | 기준선 |
| 본문 3,000자 (32B) | 58 | 약 6시간 | **항목의 34~48%가 바뀐다** |
| 본문 1,500자 (32B) | 74 | 약 5시간 | 더 나빠진다 |
| Qwen3-14B-AWQ | 미측정 (계산상 4~5배) | 약 3시간 | 재검증 필요 |

**본문을 줄이는 것은 공짜가 아니다.** 8개 문서로 기존 결과와 대조했다.

    business_keyword  기존 62개 중 41개 유지 (66%)
    rd_field          기존 48개 중 25개 유지 (52%) — 삼성전자 2021 은 8개 → 0개
    main_business     8/8 그대로 나옴

바뀐 항목이 **틀린 것은 아니다** — 원문 대조를 통과하므로 전부 문서에 있는 말이다.
짧은 창에서 다른 항목을 골랐을 뿐이다. 그래도 뒤쪽 서술을 잃는 것은 사실이고,
연구개발 섹션은 앞부분이 조직 소개라 특히 손해가 크다.

**14B 는 계산상 타당하다.** 가중치 9GB 면 KV 예산이 3.4GB → 12.6GB 로 늘고,
토큰당 80KB 라 165,000 토큰 = 동시 55개가 들어간다. CUDA 그래프도 켤 수 있다.
다만 프롬프트를 다시 맞추고 표본 검증을 해야 한다.

## 7. 만들 순서

한 번에 다 세우지 않는다. 각 단계마다 확인할 것이 있다.

| 순서 | 무엇 | 끝났다고 볼 기준 |
|---|---|---|
| 1 | EC2 2대에 Hadoop 설치, HDFS 기동 | `hdfs dfsadmin -report` 에 DataNode 2개 |
| 2 | YARN 기동 | `yarn node -list` 에 NodeManager 2개 |
| 3 | 양쪽 노드에 파이썬 환경 | `LXML_VERSION` 이 두 노드에서 같음 |
| 4 | 원문 487건 업로드 | `hdfs dfs -count` 가 487 |
| 5 | **0차 — Spark 파싱** | 결과가 지금 시드와 **완전히 같음** |
| 6 | Kafka 설치·토픽 생성 | `kafka-topics --describe` 에 파티션 4 |
| 7 | LLM 컨슈머 연결 | 0차 100개사가 큐를 타고 끝까지 감 |
| 8 | 1차 300개사 → 2차 1,000 → 3차 전체 | 차수마다 파싱 성공률 확인 |

**5번(0차)이 가장 중요하다.** 인프라를 바꾸면서 결과까지 바뀌면 Spark 탓인지 파서
탓인지 못 가린다. 지금 100개사 결과가 시드로 커밋돼 있어 대조할 수 있고, 대조 도구
(`scripts/compare_parse_output.py`)와 절차서(PHASE0)는 이미 준비돼 있다.

**6·7번을 5번 뒤에 두는 이유**도 같다. 파싱이 맞는 것을 확인한 뒤에 큐를 얹어야
문제가 생겼을 때 어디를 볼지 안다.

## 8. 장애가 나면

| 어디가 죽나 | 어떻게 되나 | 복구 |
|---|---|---|
| Spark 태스크 | YARN 이 그 태스크만 재시도 | 자동 |
| Spark 잡 전체 | HDFS 원문은 그대로 | 잡 재실행 (파싱은 멱등) |
| Kafka 브로커 | 컨슈머 멈춤. 토픽은 디스크에 있음 | 브로커 재기동 → 오프셋부터 |
| LLM 컨슈머 | 처리 중 메시지가 커밋 안 됨 | 컨슈머 재기동 → 그 메시지부터 |
| vLLM (GPU) | 컨슈머가 HTTP 실패 → 재시도 | `vllm-setup.sh start` |
| 개발 PC | 수집·오케스트레이션만 멈춤 | 이어받기 |

**원문(HDFS)만 살아 있으면 어느 단계든 다시 만들 수 있다.** 그래서 원문을 불변으로
두고 덮어쓰지 않는다.

## 10. 아직 확인 못 한 것 · 요청

### (1) EC2 → jupyter05:8000 접근 — 인프라 담당 확인

컨슈머를 어디 둘지가 여기서 갈린다. **구조는 바뀌지 않는다** — 컨슈머는 Kafka
클라이언트 + HTTP 클라이언트라 어디서 돌든 같다.

```bash
# EC2 에서
curl -s -o /dev/null -w '%{http_code}\n' --max-time 10 http://70.12.130.105:8000/health
```

`200` 이면 컨슈머를 EC2 에, 타임아웃이면 개발 PC 에 둔다. **기본값은 개발 PC** 다 —
이미 되는 경로라 이것 때문에 일정이 막히지 않는다.

### (2) GPU 쪽 — 답변 받음 (2026-09-10)

| 물은 것 | 답 |
|---|---|
| 배치 시간대 | **제한 없음.** 8~12시간 연속 점유 가능. 팀 내 다른 사용은 배치 동안 멈춘다 |
| vLLM 인자 | 6장 표에 기록. `max_num_seqs` 는 병목이 아니고 **KV 캐시가 병목**이다 |
| 재시작 권한 | **있다.** 우리 팀 전용 인스턴스. 제약 셋은 6장 |
| GPU 추가 | **불가.** 캡처의 0MiB 는 그 순간이었을 뿐이고 지금은 GPU 0·2 도 다른 팀이 쓴다 |

**속도 편차의 원인이 밝혀졌다.** 메모리가 아니라 **연산 경합**이다. 메모리는 절반씩
나뉘어 있지만 연산 코어는 같은 카드를 두 팀이 나눠 쓴다. 시간대를 골라도 통제할 수
없으므로 **11~12시간으로 잡는다.**

### (3) 남은 판단 — 시간을 줄일 것인가 (데이터 담당)

GPU 를 더 받을 수 없고 동시성도 이득이 없으니, 남은 선택은 둘뿐이다.
실측은 6장에 있고 요약하면 이렇다.

| 선택 | 11,395건 | 대가 |
|---|---|---|
| **그대로 (권장)** | 11~12시간 | 없음. 하룻밤 배치로 끝난다 |
| 본문 3,000자 | 약 6시간 | 항목의 34~48%가 바뀐다. 삼성전자 2021 rd_field 는 8개 → 0개 |
| Qwen3-14B-AWQ | 약 3시간 | 프롬프트 재조정 + 표본 검증. main_business·strategy_change 는 자동 대조가 안 돼 사람이 봐야 한다 |

**지금은 그대로 가는 것을 권한다.** 배치 시간대 제한이 풀렸으므로 11~12시간은
하룻밤이면 끝나고, 품질을 흔들 이유가 없다. `main_product` 를 뺀 다섯 항목은 화면에
그대로 노출되는 글이라 검증 비용이 싸지 않다.

**다시 볼 조건**은 정해 둔다. 아래 중 하나라도 걸리면 14B 실험을 한다.

- 프롬프트를 고쳐 **전체를 다시 돌려야 하는 일이 두 번 이상** 생긴다
- 분기마다 재실행하기로 정해진다 (연 1회면 11시간은 문제가 아니다)
- 뉴스 등 다른 LLM 작업이 같은 GPU 를 나눠 써야 한다

14B 실험은 **한 시간이면 판단이 선다.** 지금 100개사 결과가 32B 로 만들어져 있어
비교 기준이 이미 있고, 목록형 항목은 원문 대조가 자동으로 걸린다. 30개 문서만
14B 로 돌려 이 문서 6장과 같은 방식으로 유지율을 재면 된다.
