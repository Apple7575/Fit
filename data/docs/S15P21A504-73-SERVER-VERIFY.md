## 1. "서버에서 돌린다" 는 이미 배선돼 있었습니다

| | 왜 | 오늘 어떻게 했나 |

## 2. ① 사업보고서 — 0차 실험 통과

대상은 100개사 × 5개년 = **원문 487건(2.95GB)** 입니다.

### 2.1 Spark 는 결과를 바꾸지 않습니다

같은 노드에서 **단일 프로세스**로 돌린 산출과 **Spark 8파티션**으로 돌린 산출을
전수 대조했습니다.

```
[OK] segment_revenue   동일 — 1,142행
[OK] facility          동일 — 1,419행
[OK] main_product      동일 — 3,946행
[OK] rd_expense        동일 —   373행
[OK] parse_summary     동일 —   487행
전부 동일 — 인프라를 바꿔도 결과가 같다
```

확인 삼아 `노트북 vs Spark` 도 돌렸는데, `노트북 vs 서버 단일프로세스` 와 **차이
목록이 완전히 같았습니다.** Spark 가 만들어낸 차이는 **0건**이라는 뜻입니다.

### 2.2 남은 차이 72건 — 원인은 원문 인코딩입니다

노트북(Windows)과 서버(Linux)는 487건 중 **72건(15%)** 에서 갈립니다. 원인이 거의
한 곳으로 모입니다.

| | |
|---|---|
| 원문 487건 중 **`encoding="utf-8"` 라고 선언해놓고 실제로는 CP949** 인 것 | **79건 (16%)** |
| 노트북과 서버 산출이 갈린 문서 | **72건 (15%)** |
| └ 그중 인코딩이 어긋난 문서 | **71건** |
| └ 인코딩은 정상인데 갈린 문서 | **1건** |
| 인코딩이 어긋났는데도 결과는 같은 문서 | 8건 |

선언과 실제가 다르면 파서가 `recover=True` 로 복구하는데, **그 복구 동작이 libxml2
버전마다 다릅니다** (노트북 2.11.9 · 서버 2.14.6).

```
노트북(2.11.9)   '해양플랜트'          '엔진기계'
서버 (2.14.6)    '해 양&cr;플 랜 트'     '엔 진 기 계'
```

`&cr;` 은 원문에 들어 있는 **정의되지 않은 엔티티**입니다(위 문서 한 건에만 2,458번).
서버 쪽이 틀린 것이 아니라 **원문의 쓰레기를 치우지 않은 것**이고, 노트북 쪽이
우연히 치워주고 있었습니다.

**실질 영향은 작습니다.**

| 무엇이 달라졌나 | 건수 |
|---|---|
| 본문 길이(`rd_chars` 58 · `business_chars` 45)만 다름 | 대부분 |
| 뽑힌 **개수**가 달라진 문서 | **7건** (부문 3 · 시설 2 · 제품 2) |
| **판정**이 뒤집힌 문서 | **2건** |
| `rd_expense` (R&D 금액) | **373행 완전 일치 — 영향 0** |

갈린 텍스트 행의 대부분이 엔티티를 품고 있습니다 — `main_product` 는 70행 중 **65행**,
`facility` 는 75행 중 57행입니다.

### 2.3 lxml 버전 고정으로는 못 막습니다

`requirements.txt` 는 `lxml==6.1.2` 로 못 박아 두고 "이러면 양쪽이 같아진다"고
적어놨는데, **그 전제가 틀렸습니다.**

| | lxml | libxml2 |
|---|---|---|
| 노트북 (Windows) | 6.1.2 | **2.11.9** |
| 서버 (Linux) | 6.1.2 | **2.14.6** |

같은 `lxml==6.1.2` 인데 libxml2 가 다릅니다. **wheel 이 libxml2 를 정적으로 품고
있고, 그 버전은 플랫폼이 정하기 때문입니다.** 버전 핀으로는 해결되지 않습니다.

(서버 venv 는 원래 `lxml 6.1.3` 이었습니다 — 인프라 구축 때 옛 `requirements.txt`
(`lxml>=5.0`)로 설치돼 있었고, 오늘 6.1.2 로 맞췄습니다. 그래도 libxml2 는 위와 같이
남습니다.)

### 2.4 그래서 제안 — 파서가 치우게 합니다

**어느 플랫폼에서 돌려도 같은 값이 나오게** 파서 쪽에 정리 단계를 넣는 것을
권합니다.

- 표 셀 텍스트에서 미정의 엔티티(`&cr;` 등) 제거
- 연속 공백 정리 (`'엔 진 기 계'` → `'엔진기계'`)
- 고친 뒤 양쪽에서 다시 돌려 **72건이 0건이 되는지 확인**

작업량은 한 시간 정도입니다. 이걸 하면 0차가 **완전 통과**가 되고, 이런 비교를
다시 할 일이 없어집니다.

> **지금 정하지 않으면 생기는 일** — 전 종목 파싱을 서버에서 돌리는 순간 텍스트
> 시드가 지금 커밋된 값과 달라집니다. 데이터를 다시 만든 뒤에 발견하면 비쌉니다.

## 7. 성능 실측 — SCALE-PLAN 을 고쳐야 합니다

487건 Spark 실행 **22분 7초**. 태스크 8개 소요는 `371 · 328 · 311 · 289 · 269 · 198 ·
185 · 2.2` 초, 재시도·실패 0건이었습니다.

```
487건 실측              22분      (파싱 슬롯 2개)
isEmpty 수정 후         약 18분
전 종목 11,395건 환산    약 7시간   ← SCALE-PLAN 은 "슬롯 6에서 2.2시간"
파싱 슬롯 4개로 늘리면    약 3.5시간
```

**차이의 원인은 슬롯 수입니다.** 설계는 EC2 2대에 슬롯 6을 전제했는데, 실제로는
NodeManager 가 `ha-master` 한 대이고(1호기는 prod·Jenkins 와 경합해 저장만 맡김)
YARN 에 vcore 3개 · 메모리 6,144MB 가 할당돼 있습니다. client 모드 AM 몫을 빼면
**executor 는 5,120MB × 2코어 하나가 최대**입니다.

**다만 전체 일정에는 영향이 없습니다.** 뒤에 붙는 LLM 이 11~12시간이고 파싱과 겹쳐
돌릴 수 있어서, 파싱이 7시간이든 3.5시간이든 **바닥은 여전히 LLM** 입니다.
