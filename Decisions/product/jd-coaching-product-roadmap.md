## 문제

직무 분석, 기업 RAG와 멀티에이전트 화면을 어떤 순서로 구현해야 기능 실험이 뒤섞이지 않고 실제 서비스까지 도달할 수 있는가.

## 검토한 선택지

1. 화면에 표시된 역할별 에이전트를 먼저 모두 구현한다.
2. 2,700개 기업의 JD와 기업 자료부터 모두 수집한다.
3. 직무 분석 기준선을 확정한 뒤 JD 입력, 기업 RAG, 통합 분석, 수정 대화, 화면 연동 순으로 확장한다.

## 트레이드오프

- 역할을 먼저 분리하면 화면 구조는 빨리 맞출 수 있지만 품질 향상 여부를 비교할 단일 기준선이 없다.
- 전체 기업 데이터를 먼저 모으면 범위는 넓어지지만 실제 사용량을 모르는 상태에서 수집 비용이 커진다.
- 기준선부터 확정하면 초기 화면 구현은 늦어지지만 기능별 성능과 실패 원인을 측정하고 MR을 작게 유지할 수 있다.

## 결정

다음 순서를 유지한다.

1. 직무 분석 기준선과 다기업 평가 라벨 확정
2. 현재 직무 분석 브랜치 정리와 MR
3. JD 원문·URL·파일 입력 경로
4. 기업 RAG의 조건부 보조 기능 연결과 기업 범위 확대
5. 직무 분석과 기업 RAG를 묶는 통합 분석 API
6. 부족한 경험 질문과 근거 기반 수정안
7. 화면 연동
8. 단일 조정기와 멀티에이전트 구조 비교
9. LLM Judge·사람 평가·회귀 평가
10. 배포와 운영 준비

서비스의 최종 입력 단위는 회사, 직무, 실제 JD와 자소서 한 개다. 기업 RAG는 자소서에 검증할 기업 사실 주장이 있을 때만 호출한다. 에이전트 분리는 단일 조정기보다 품질이 좋아진다는 평가 결과가 있을 때 선택한다.

## 이유

현재 직무 분석 엔진과 기업 사실 검증 API는 각각 존재하지만 통합 서비스 성능은 아직 측정되지 않았다. 기준선을 먼저 확정해야 이후 JD 수집, 기업 RAG와 멀티에이전트가 실제 개선인지 비교할 수 있다. 또한 기능별 MR을 분리해 리뷰 범위를 통제할 수 있다.

## 재검토 조건

- 실제 화면의 필수 입력 또는 백엔드 API 계약이 바뀐다.
- 다기업 평가에서 현재 직무 분석이 최소 품질 기준을 통과하지 못한다.
- 기업 RAG 사용률이나 기업 데이터 커버리지가 낮아 보조 기능 유지 비용이 가치보다 커진다.
- 멀티에이전트 비교에서 근거 충실도나 행동 가능한 피드백이 향상되지 않고 시간·비용만 증가한다.
- 실제 사용자 이용 분포가 확보되어 JD 수집 기업 우선순위를 다시 정할 수 있다.
