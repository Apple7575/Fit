## 문제

기존 Spring의 짧은 글쓰기 피드백을 확장하지 않고 Python AI 영역에서 실제 수정문,
변경 이유와 후속 대화를 제공하려면 글쓰기 담당의 범위, 사실 근거, API 상태와 총괄 실행
순서를 결정해야 했다.

## 검토한 선택지

1. 기존 초안의 문장과 구조만 첨삭한다.
2. 사용자 경험 자료를 바탕으로 초안 없이 완성 자소서를 생성한다.
3. 첨삭과 신규 작성을 모두 지원한다.
4. 단일 Qwen 호출과 결정적 검증을 사용하는 독립 서비스를 만든다.
5. 글쓰기 담당 내부에도 다단계 LangGraph를 둔다.
6. 기존 Spring 글쓰기 프롬프트를 확장한다.
7. 일회성 수정 API만 제공한다.
8. 최근 대화를 호출자가 전달하는 무상태 대화 API를 제공한다.

## 트레이드오프

- 기존 초안 첨삭은 사실 생성 위험과 범위를 통제하기 쉽지만 원문에 없는 경험을 보완할
  수 없다.
- 신규 작성은 사용 편의성이 높지만 경험을 과장하거나 지어낼 위험이 크다.
- 글쓰기 내부 LangGraph는 단계별 검토가 가능하지만 호출 시간, 비용과 실패 지점이 늘어난다.
- Spring 확장은 구현량이 작지만 구조화 결과 검증과 Python 분석 worker 연계가 어렵다.
- 무상태 대화는 별도 DB 없이 반복 첨삭과 설명을 지원하지만 백엔드가 최신 초안과 최근
  대화를 매번 조립해야 한다.
- Writing을 분석 worker와 병렬 실행하면 빠르지만 아직 생성되지 않은 피드백을 반영할 수
  없다. 분석 뒤에 실행하면 지연은 늘지만 진단을 실제 수정으로 연결할 수 있다.

## 결정

- V1은 자소서 문항 한 개의 기존 초안 첨삭과 재작성만 지원한다.
- 문항 선택은 백엔드가 담당하고 글쓰기 AI에는 문항 내용, 기준 초안과 글자 수를 전달한다.
- 다른 에이전트 피드백은 선택 입력이며 없으면 순수 문장 첨삭을 수행한다.
- 좋은 자소서는 질문에 직접 답하고 실제 경험으로 직무 관련 역량과 기여를 빠르고 명확하게
  전달하며, 과장 없이 본인의 목소리를 유지하고 제출 조건을 지키는 글로 정의한다.
- 첨삭 유형은 구조, 명료성, 간결성, 흐름, 문체와 분량으로 제한한다.
- `LIGHT`, `BALANCED`, `REWRITE`를 사용자 요청에서 판단하며 불명확하면 `BALANCED`다.
- 현재 초안, 현재 사용자 메시지와 이전 USER 메시지만 새로운 사실의 근거로 인정한다.
  ASSISTANT 메시지와 worker 피드백은 사실 근거가 아니다.
- 독립 Python 무상태 대화 API는 `REVISED`, `ANSWERED`,
  `CLARIFICATION_REQUIRED`를 반환한다. 대화 DB와 수정 결과 저장은 만들지 않는다.
- 단일 Qwen 구조화 호출과 결정적 검증을 사용하고, 검증 실패 시 한 번만 재시도한다.
- 총괄 에이전트에 `writing` worker를 등록하고 JD·Position 분석 뒤에 순차 실행한다.
- Spring 백엔드, 프런트엔드와 DB는 이번 구현에서 수정하지 않는다.

## 이유

현재 제품의 분석 결과를 실제 수정 행동으로 연결하면서도 사용자 경험을 대신 만들어내지
않기 위해서다. 독립 무상태 서비스는 개별 API와 총괄 worker에서 같은 품질 규칙을 재사용할
수 있고, 별도 저장소 없이 현재 백엔드가 가진 문항·대화 수명 주기를 유지한다. 분석 worker를
먼저 실행하면 JD와 직무 진단을 손실 없이 첨삭 방향으로 사용할 수 있다.

## 재검토 조건

- 여러 문항의 동시 첨삭이나 문항 간 일관성 검사가 필요해진다.
- 승인 전 수정 후보와 대화를 AI 서버가 지속적으로 저장해야 한다.
- 초안 없는 신규 작성이나 별도 경험 발굴이 제품 범위에 포함된다.
- 외부 채용 사이트별 글자 수 계산 정책이 필요하다.
- 단일 생성과 한 번의 재시도로 품질이 안정되지 않는다.
- 동기 호출 시간이 운영 HTTP 제한을 반복적으로 초과한다.
