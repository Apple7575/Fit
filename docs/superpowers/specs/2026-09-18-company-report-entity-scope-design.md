# 사업보고서 표의 법인 범위 보존 설계

## 목표와 확인된 원인

기업 분석 보고서가 자회사 표의 숫자를 지주사 전체 실적으로 서술하지 못하게 한다. 우리금융지주 2025년 사업보고서의 `22,133백만원`은 원본 XML에서 `【 우리자산운용 】` 아래의 영업실적 표에 있다. 기존 청크에는 `3. 재무상태 및 영업실적`이라는 상위 장 제목만 있어 소속 법인 정보가 사라졌다. 숫자·단위 일치 검사는 이를 발견할 수 없다.

디에이피의 최신 실적 상세 6건 탈락은 별도 원인 조사로 남긴다. 과거 출력에는 숫자의 마지막 세 자리를 잘라 쓴 오류가 있었지만, 최신 6건의 생성 원문은 저장되지 않았다. 로컬 PostgreSQL은 현재 Docker Desktop 백엔드 오류로 실행할 수 없다.

## 범위

- DART 사업보고서의 명시적인 소속 법인 제목을 표와 연결한다.
- 해당 정보를 검색 결과와 생성 입력에 제공하고, 자회사 표에서 나온 수치를 기업 전체 수치로 서술하면 제외한다.
- 기존 100개사 DB와 1024차원 임베딩은 재계산하지 않는다.
- 뉴스 수집·뉴스 섹션은 별도 에이전트 범위이며 이 변경에 포함하지 않는다.
- 명시적 제목이 없는 표의 소속을 기업명이나 주변 수치로 추정하지 않는다.

## 데이터 흐름

1. XML 파서는 같은 `TITLE` 구간 안에서 `【 법인명 】` 형태의 문단을 만나면 현재 소속 법인으로 기억한다. 다음 명시적 법인 제목 또는 `TITLE` 변경 전까지 뒤따르는 표에 적용한다. 단위·표 제목·일반 문장은 법인 제목으로 취급하지 않는다.
2. 기존 `rag_evidence`의 `content`, `metadata`, `content_hash`는 수정하지 않는다. 별도 `rag_evidence_entity_scope` 테이블에 `evidence_id`, 명시적 소속 법인명, XML 접수번호·표 인덱스, 추출 규칙 버전을 저장한다. 원본 XML과 안정적인 근거 ID를 이용해 멱등적으로 적재한다. 참조 대상 근거가 없는 행은 적재하지 않고 수량을 보고한다.
3. API의 PostgreSQL 조회는 소속 범위를 `LEFT JOIN`으로 받아 `EvidenceDocument`의 별도 필드에 넣는다. 기존 벡터 적합성 검사에 쓰는 근거 해시와 임베딩 해시는 그대로 유지한다. 생성 모델에는 원문 표와 함께 `소속 법인`을 명시한다.
4. 생성 후 검증은 소속 법인이 붙은 표의 금액을 인용한 문장에 그 법인명이 없거나, 해당 수치를 대상 기업의 `전체`·`연결 전체` 실적으로 명시하면 해당 상세를 제외한다. 이 표 외에 독립적인 전체 실적 근거가 함께 인용되었다면 검증은 그 독립 근거를 별도로 평가한다. 근거가 불명확하면 수치를 쓰지 않는다.

## 실패·호환성 처리

- 소속 범위가 아직 적재되지 않은 근거는 기존 동작을 유지하지만, 범위 안전성이 검증됐다고 간주하지 않는다. 적용 상태를 평가 결과에 표시한다.
- 새 테이블이 없는 DB에서는 배포 전에 마이그레이션을 실행해야 한다. 마이그레이션 실패 시 조용히 범위 검증을 건너뛰지 않고 설정 오류로 종료한다.
- 소속 법인 제목이 다른 기업의 명칭과 비슷하더라도 문자열 포함만으로 동일 법인이라고 판정하지 않는다. 우선 원문 명칭을 그대로 전달하며, 별칭 매핑은 평가셋에서 필요성이 확인될 때 별도 설계한다.
- 로컬 DB 복구 전에는 XML 파서·적재 매핑·API 검증을 단위 테스트로 검증한다. DB가 복구되면 100개사 백필 결과의 건수와 우리금융지주 보고서를 실제 재생성한다.

## 검증 기준

- 작은 합성 XML에서 법인 제목이 여러 번 바뀌거나 `TITLE`이 바뀔 때 각 표의 소속이 정확히 달라진다.
- 실제 우리금융지주 원본에서 `22,133백만원` 표의 소속은 `우리자산운용`으로 추출된다.
- 소속 범위 적재 전후 기존 `rag_evidence.content_hash`와 `rag_evidence_embedding.content_hash`의 일치 상태가 변하지 않는다.
- 자회사 표만 인용한 `우리금융지주 전체 영업이익 22,133백만원`은 탈락하고, `우리자산운용 영업이익 22,133백만원`은 숫자·단위 검사까지 통과한다.
- 디에이피는 로컬 DB가 복구되면 삭제 전 생성 문장과 위반 코드를 확보해 원인을 판정한다. 이 설계만으로 디에이피 문제가 해결됐다고 주장하지 않는다.
