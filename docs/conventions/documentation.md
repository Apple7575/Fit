# 문서 작성 컨벤션 — 의사결정 기록

되돌리기 어렵거나 "왜 이렇게 했지?"라는 질문이 나올 결정을 짧게 남긴다.
이 기록은 그대로 **포트폴리오의 근거**(문제 → 판단 → 결과)가 된다.

## 어디에 쓰나

- 한 파트 안에서 끝나는 결정 → `<part>/docs/decisions/`
  `backend/docs/decisions/`, `frontend/docs/decisions/`, `infra/docs/decisions/`, `data/docs/decisions/`
- 여러 파트에 걸치는 결정(API 계약, 브랜치 전략 등) → `docs/decisions/`

## 파일 이름

`NNNN-<제목-kebab>.md` — 디렉토리별 4자리 일련번호.
예) `backend/docs/decisions/0001-metric-long-table.md`

## 무엇을 기록하나

- **기록한다**: 아키텍처 · 데이터 모델 · 기술 선택 등 트레이드오프가 있는 결정.
- **기록하지 않는다**: 코드만 봐도 아는 것, 사소한 선택 → 코드 주석이나 PR 설명으로.
- 결정 1개 = 파일 1개.

## 형식

아래 네 항목이면 충분하다. 그대로 복사해서 쓴다.

```markdown
# NNNN. <결정을 한 문장으로>

- 상태: 제안 | 채택 | 폐기 | 대체됨(→ NNNN)
- 작성자: <이름>  (여러 명이 함께 결정했으면 쉼표로 나열, 주도한 사람을 맨 앞)
- 날짜: YYYY-MM-DD
- 관련 이슈: S15P21A504-<번호>

## 배경
왜 이 결정이 필요했나. 문제와 제약을 2~4문장.

## 결정
무엇을 택했나. 한 문단.

## 대안과 근거
고려한 다른 선택지와 탈락 이유. (포트폴리오의 핵심 — "왜"를 남긴다.)

## 결과
적용 후 효과, 남은 트레이드오프, 후속 과제.

## AI 활용 (선택)
어떤 판단에 AI를 어떻게 썼고, 그 결과를 무엇으로 검증했는지. AI를 안 썼으면 생략한다.
```

## 규칙

1. **채택된 기록은 고치지 않는다.** 결정이 바뀌면 새 파일을 쓰고, 옛 파일의 상태만 `대체됨(→ 새 번호)`으로 바꾼다. 판단의 이력이 남아야 포트폴리오로 쓸 수 있다.
2. **"왜"를 반드시 남긴다.** 무엇을 했는지보다 왜 그 선택인지가 가치다.
3. **핵심만, 구체적으로.** 한글 평서문. 근거가 되는 수치·코드·링크는 구체적으로, 나머지는 생략한다.
4. **작성자를 반드시 적는다.** 포트폴리오에서 본인 기여를 가리는 근거다. 여러 명이 함께 결정했으면 모두 적되 주도한 사람을 맨 앞에 둔다. (Git 이력은 Squash merge로 뭉개지므로 문서 안에 남긴다.)
